# 架构设计

## 1. 目标与范围

### 1.1 功能

| 场景 | 能力 |
|---|---|
| 分区恢复 | 读取并检查分区表；快速搜索与深度搜索丢失的分区；生成并写入新的分区表 |
| 分区修复 | 引导扇区检查、从备份恢复、重建（FAT、NTFS、exFAT、HFS/HFS+、ext 超级块）；FAT 表修复；NTFS MFT 从镜像修复；写入 MBR 引导代码 |
| 文件找回 | 浏览分区目录、复制文件、反删除（FAT、exFAT、NTFS、ext2/3/4） |
| 深度恢复 | 不依赖文件系统，按文件签名在整盘、分区或未分配空间中恢复数百种格式；块大小探测；暴力恢复；断点续传；恢复报告 |
| 文件系统检查与修复 | exFAT、FAT12/16/32 的完整一致性检查：引导区与校验和、FAT 链、分配位图、目录项集合与校验和、大写表，以及交叉链接、丢失簇、越界与循环链。先列出问题清单，用户勾选后生成修复计划；可标记坏簇，孤立的簇链可另存为文件。NTFS 只做有把握的部分（引导扇区、MFT 镜像） |
| 磁盘镜像 | 能识别坏区的镜像：首轮遇错跳过并记入坏区图，先读完完好区域，之后多轮缩小读取粒度回头重试；可暂停、断点续传；坏区图随镜像保存。在镜像上可以执行以上全部操作 |

支持范围：

- **分区表**：MBR（含扩展分区）、GPT、Apple 分区图、Sun、Xbox、Humax、无分区表。
- **文件系统识别**：APFS、BeFS、BSD disklabel、Btrfs、CramFS、exFAT、ext2/3/4、FAT12/16/32、FATX、F2FS、JFS、GFS2、HFS、HFS+、HPFS、LUKS、LVM/LVM2、Linux RAID、NetWare NSS、NTFS、ReFS、ReiserFS、Sun、Linux Swap、System V、UFS/UFS2、VMFS、WBFS、XFS、ZFS。
- **镜像格式**：raw/dd、分段 raw、E01。
- **平台**：Windows 10/11、macOS、Linux 桌面。

### 1.2 质量目标

高可用、鲁棒、安全、高性能、美观、易用。每一项的设计约束见第 8 节。

### 1.3 数据安全原则

- **默认只读。** 所有写盘操作都先生成写入计划，经用户确认后执行（第 4.2 节）。
- **磁盘报读错误时，先镜像，后修复。** 一旦检测到介质错误，界面建议先制作镜像（第 5.6 节）；检查、修复、恢复都在镜像上进行，是否改动原盘由用户最后决定。对出错的盘反复读写会加重损坏。
- **检查与修复分开。** 检查阶段只读，随时可以取消；修复只处理用户勾选的问题，并且改前备份、改后读回校验。

## 2. 总体架构

```
┌──────────────────── 界面进程（普通权限）────────────────────┐
│  Tauri 2 宿主（Rust）  ⇄  界面（Vue 3 + TypeScript）         │
│  任务管理 · 进程守护 · 事件节流 · 本地任务记录               │
└──────────────┬──────────────────────────────┬──────────────┘
               │ JSON-RPC（stdio 管道）        │ JSON-RPC（管道，见 4.1）
┌──────────────▼──────────────────┐  ┌────────▼──────────────────────┐
│ 引擎进程（每个任务一个，普通权限）│  │ 磁盘代理（特权，代码最少）      │
│  engine   任务 / 决策 / 进度 / 取消│◄─┤  打开设备，把只读句柄交给引擎   │
│  repair   分区恢复与修复          │  │  执行写入计划                   │
│  carve    深度恢复                │  │                                 │
│  formats  文件格式插件            │  └───────────────────────────────┘
│  fs       文件系统                │
│  part     分区表                  │
│  io       块设备 / 镜像 / 缓存     │
└─────────────────────────────────┘
```

拆成三类进程的原因：

1. **解析不可信数据的代码不持有特权。** 磁盘内容可能已损坏，也可能被刻意构造。所有解析都在普通权限的引擎进程里进行，即使解析器有缺陷，也拿不到写盘或提权的能力。
2. **故障隔离。** 引擎崩溃、陷入死循环或内存失控，只影响这一个任务；界面会报告原因，可以重试或从断点续传。
3. **特权代码最少、可审查。** 只有磁盘代理持有特权，它只做两件事：打开设备、执行写入计划。列出磁盘只需查询设备属性，由引擎以普通权限完成（第 4.1 节）。
4. **桌面环境限制。** 不少 Linux 桌面（Wayland）默认不允许 root 进程直接开窗口，界面本来就不能以特权身份运行。

宿主与引擎之间走父子进程的 stdio 管道。宿主与磁盘代理之间：Linux 同样走 stdio；Windows 上提权进程接管不了 stdio，改走命名管道（第 4.1 节）。都不监听任何网络端口。

## 3. 进程与通信

### 3.1 协议

- JSON-RPC 2.0，每条消息前加 4 字节小端长度成帧，单条消息不超过 1 MiB。成帧与消息类型在 `yisi-rpc`，宿主、引擎、代理共用。
- 宿主 → 引擎：请求（启动任务、回答决策、取消）。启动任务的请求带上任务 ID（由界面生成），引擎立即答复空对象，之后的进展都以通知送达。
- 引擎 → 宿主：答复，以及不带 id 的通知：`engine.heartbeat`、`job.progress`、`job.log`、`job.completed`、`job.failed`、`job.cancelled`，以及之后的 `job.found`、`job.decision`。每条任务通知都带 `jobId`。
- `job.progress` 在引擎侧节流，每秒最多 10 次，完成那一次总会发出；`found` 事件批量合并后发出。
- 方法名、参数与结果的类型定义在 `yisi-engine` 的库部分（`protocol`），宿主直接引用，不另写一份。

### 3.2 任务生命周期

```
created → running ⇄ waiting_decision → completed
                 ↘ cancelling → cancelled
                 ↘ failed
```

- 每个任务一个引擎进程，任务结束后进程退出。宿主断开（引擎的 stdin 结束）时，引擎取消正在运行的任务后退出。
- 取消：先发 `job.cancel`，引擎在下一个检查点结束任务并发出 `job.cancelled`；5 秒内未退出时，宿主结束进程，仍按取消处理。
- 任务里的 panic 在任务边界捕获，转成 `job.failed`；引擎没有发出终结通知就退出时，宿主按失败处理并带上退出码。
- 心跳：引擎每 2 秒发一次心跳；超过 10 秒没有心跳，标记为无响应，由用户决定等待还是结束；心跳恢复后撤销标记。
- 资源上限：引擎进程设置内存上限（Windows 用作业对象，Linux/macOS 用 rlimit）。

### 3.3 决策事件

恢复流程中需要用户判断的地方（确认写入、选择分区、输入参数等），以决策事件发给界面。引擎阻塞等待答复，流程代码保持顺序写法。

```json
{"type":"decision","jobId":"j1","id":"d7","kind":"confirm","risk":"write",
 "title":"写入分区表","detail":{"before":[...],"after":[...]},
 "options":["apply","cancel"],"default":"cancel"}
```

- `kind`：`confirm`、`select`、`number`、`text`、`location`。
- **`risk` 为 `write` 的决策，默认值固定为取消；等待超时也按取消处理。**

### 3.4 RPC 方法（初版）

| 方法 | 说明 |
|---|---|
| `engine.capabilities` | 返回引擎版本和已支持的功能，界面据此显示或隐藏入口 |
| `disk.list` / `disk.openImage` | 列出物理磁盘（只查询设备属性，普通权限即可）；打开镜像文件 |
| `repair.analyse` | 读取当前分区表并检查结构 |
| `repair.search` | 快速或深度搜索分区（任务） |
| `repair.listFiles` / `repair.copyFiles` / `repair.undelete` | 浏览、复制、反删除；只读访问源盘 |

| `fs.check` | 文件系统一致性检查（任务，只读）；逐阶段推送进度，边查边推送发现的问题 |

| `job.cancel` / `job.status` | 取消任务；查询状态 |

## 4. 特权与设备访问

### 4.1 只读句柄传递

磁盘代理以特权打开设备，把**只读**句柄交给引擎：

| 平台 | 提权方式 | 句柄传递 |
|---|---|---|
| Linux | polkit（pkexec）启动代理 | Unix 套接字 `SCM_RIGHTS` |
| macOS | 系统授权服务 | 与 `authopen` 相同的描述符传递方式 |
| Windows | 代理以管理员身份运行（UAC） | `DuplicateHandle` 复制到引擎进程 |

引擎侧的块设备类型**不提供写方法**，写盘能力在类型层面就不存在于引擎中。

**Windows 的做法。** 普通权限的宿主只能用 `ShellExecuteEx("runas")` 启动提权进程，接管不了它的 stdio，所以宿主与代理之间走命名管道：

- 管道由宿主创建，名字带 128 位随机数；`FILE_FLAG_FIRST_PIPE_INSTANCE` 让抢先占用同名管道的情况直接失败，`PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程连接。
- 管道的 ACL 只允许管理员组和 SYSTEM。提权后的代理属于管理员组；未提权的进程，即使与宿主是同一用户，也连不上。
- 双向核对身份：宿主核对连进来的客户端进程就是刚启动的代理；代理核对管道的服务端进程就是命令行给出的宿主。
- 宿主退出时代理随之退出，管道关闭时代理读到结束后退出，不留下以管理员身份运行的孤儿进程。
- 代理只接受 `\\.\PhysicalDriveN` 形式的路径，不替宿主打开任意文件。
- 代理只读打开设备，用 `DuplicateHandle(…, DUPLICATE_SAME_ACCESS)` 复制进引擎进程，复制出的句柄与原句柄一样只有读权限（实测授予的权限为 `FILE_GENERIC_READ`）。
- 引擎用 `WindowsDisk::adopt_handle` 认领句柄：只接受能回答磁盘 IOCTL 的句柄，同一个值只能认领一次。引擎自己没有权限打开磁盘，这类句柄只能来自代理。

macOS 的特权辅助程序同样没有 stdio，通道在实现 macOS 版时确定（XPC）。

**列出磁盘不需要特权。** Windows 允许普通权限以零访问权限打开 `\\.\PhysicalDriveN`，只查询设备属性、不读写内容：容量与逻辑扇区大小用 `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX`，厂商、型号、序列号、总线与是否可移动用 `IOCTL_STORAGE_QUERY_PROPERTY`。所以 `disk.list` 由引擎完成，用户选好盘、真正要读的时候才需要代理。

**扫描一块物理磁盘的流程（Windows）：**

1. 宿主启动引擎，得到它的进程 ID；
2. 宿主确保代理在运行：第一次需要时提权启动（弹 UAC），之后整个会话复用；代理通信失败时丢掉连接，下次重新启动；
3. 代理只读打开磁盘，把句柄复制进这个引擎；
4. 宿主向引擎发起任务，源为 `{type: "disk", handle}`，引擎用 `WindowsDisk::adopt_handle` 认领后照常读取。

### 4.2 写入计划

所有写盘操作都先由引擎生成写入计划，经用户确认后交给代理执行：

```rust
pub struct WritePlan {
    pub id: PlanId,
    pub device: DeviceIdentity,      // 序列号、容量、扇区大小，防止写错盘
    pub writes: Vec<SectorWrite>,    // 起始扇区、新内容、写前内容的 SHA-256
    pub summary: PlanSummary,        // 给界面展示的修改前后对比
}
```

代理按以下步骤执行，任何一步失败都停止，并报告停在哪一步：

1. 核对设备身份与计划一致；
2. 读取目标扇区，核对写前哈希。不一致说明磁盘在计划生成后被改动过，拒绝执行；
3. 把原扇区内容和元数据写入备份文件；
4. 写入并刷盘；
5. 读回校验；
6. 记录执行结果。

回滚就是把备份文件当成一份新的写入计划执行。

## 5. 引擎模块

### 5.1 模块与依赖方向

```
io ← part ← fs ← repair ─┐
          ↖ formats ← carve ├─ engine
                          ┘
io ← broker
rpc ← engine、broker、宿主（宿主另外引用 engine、broker 的库部分）
```

| 目录 | 包名 | 职责 |
|---|---|---|
| `crates/io` | `yisi-io` | 块设备抽象；Windows/macOS/Linux 后端；raw、分段 raw、E01；读缓存；坏扇区读取策略；能识别坏区的镜像（第 5.6 节） |
| `crates/part` | `yisi-part` | 分区表的解析、校验、序列化与自动识别 |
| `crates/fs` | `yisi-fs` | 文件系统识别；目录读取与文件提取；空闲空间位图；引导扇区与超级块的检查和重建；exFAT / FAT 一致性检查（只读，输出问题清单，第 5.7 节） |
| `crates/formats` | `yisi-formats` | 文件格式插件与注册表 |
| `crates/carve` | `yisi-carve` | 深度恢复：搜索空间、块大小探测、识别分派、数据检查、暴力恢复、断点续传、恢复报告 |
| `crates/repair` | `yisi-repair` | 分区分析与搜索、结构检查、反删除；生成写入计划（分区表、引导扇区、FAT/MFT 修复、文件系统修复） |
| `crates/engine` | `yisi-engine` | 引擎进程入口：任务运行时、决策事件、进度节流、取消。库部分只有宿主与引擎之间的方法与参数（`protocol`），供宿主引用 |
| `crates/broker` | `yisi-broker` | 磁盘代理。库部分供宿主使用：方法与参数、Windows 上建管道和提权启动；程序部分是以管理员身份运行的代理本身 |
| `crates/rpc` | `yisi-rpc` | 成帧与 JSON-RPC 2.0 消息，宿主、引擎、代理共用 |

**unsafe 边界**：只有 `io` 和 `broker` 允许 `unsafe`，用于平台系统调用，每处都要写清安全性论证；其余模块一律 `#![forbid(unsafe_code)]`。

### 5.2 块设备抽象

```rust
pub trait BlockDevice: Send + Sync {
    fn size(&self) -> u64;
    fn sector_size(&self) -> u32;
    fn read_at(&self, offset: u64, buf: &mut [u8]) -> Result<usize, IoError>;
    fn read_exact_at(&self, offset: u64, buf: &mut [u8]) -> Result<(), IoError>; // 有默认实现
}
```

- `read_at` 的偏移和长度不要求按扇区对齐；读到设备末尾时截断，偏移不小于容量时返回 0。`read_exact_at` 读不满时返回带偏移的错误，供解析器使用。
- 物理盘只接受起点、长度、缓冲区地址都按扇区对齐的读请求。后端在内部处理：请求本身已经对齐时直接读进调用方的缓冲区，否则经对齐的中转缓冲区（每次最多 1 MiB）读取再拷贝。
- Windows 后端以只读、共享读写的方式打开 `\\.\PhysicalDriveN`，不加锁、不独占；容量和逻辑扇区大小用 IOCTL 查询。
- 镜像文件不记录扇区大小，打开时由调用方给出（取来源磁盘的逻辑扇区大小）。扇区大小只接受 512 到 64 KiB 之间的 2 的幂。
- 读错误带上偏移和系统错误码，供坏区策略识别介质错误。
- 读错误按策略处理：重试次数、超时、跳过并记入坏区表，都可以配置。
- 读缓存按扇区对齐；镜像文件优先用内存映射。

### 5.3 文件格式插件

```rust
pub trait FileFormat: Send + Sync {
    fn info(&self) -> &FormatInfo;          // 扩展名、描述、最大尺寸、默认启用
    fn signatures(&self) -> &[Signature];   // (偏移, 魔数)
    fn header_check(&self, block: &[u8]) -> Option<Box<dyn Recovering>>;
}

pub trait Recovering: Send {
    fn data_check(&mut self, offset: u64, block: &[u8]) -> DataCheck; // 继续 / 在某长度处结束 / 无效
    fn open_ended(&self) -> bool;                // 没有结束标志（如 PDF）：遇到下一个文件头时收尾
    fn finish(&mut self, received: u64) -> Option<u64>; // 数据到此为止时的文件长度
    fn waiting_at(&self) -> Option<u64>;         // 正在等待的位置，用来尽早排除长度离谱的误识别
}
```

- **结构遍历器**：大多数格式的插件只实现一个小状态机，每一步告诉遍历器「下一步要从哪里开始的几个字节」（`Need`）、「从哪里开始找什么」（`Scan`）、「文件在这里结束」（`Done`）或「无效」。跨块拼接、跳过大段数据、跨块查找都由遍历器处理，插件不必关心数据怎么分块。遍历器保留最近一次交付或匹配处的字节，插件可以先读签名、再从同一位置读整条记录。
- 一个格式一个源文件，自带样本测试。样本由代码按格式结构现场生成（`yisi-formats` 的 `test-samples` 特性），不放二进制样本进仓库；每个格式还要过同一组随机与变异输入测试，只能给出结果或「不认识」，不能 panic。
- 注册表在启动时把全部签名建成「偏移 + 前两个字节」的查找表，每个块只查表，不遍历格式。
- 界面上的格式列表来自 `carve.listFileTypes`，不在界面里硬编码。
- 按内容给文件命名（`rename`）在后续加入。

### 5.4 深度恢复流水线

```
读线程 ──(块环形缓冲)──▶ 恢复线程 ──(输出队列，带背压)──▶ 写线程
大块、对齐、顺序读         查签名表、跑格式状态机          写出恢复文件
预读                       维护搜索空间                    检查输出盘空间
```

- 同一块物理盘只有一条顺序读流，避免磁头来回寻道，也减轻对故障盘的压力。
- 读盘、计算、写出三者并行。
- 不同物理盘的任务各开一个引擎进程，可以并行。
- 输出盘空间不足时自动暂停并通知界面。
- 定期写入断点，异常退出后可以续传。

**目前的实现（线性恢复，只处理连续存放的文件）：**

- 按 1 MiB 读设备，再按扇区大小的块处理；文件只可能从块边界开始。整段读不出时逐块重读，只跳过真正读不出的块，正在恢复的文件随之放弃。
- 块开头命中文件头时开始恢复，后续块交给插件判断结尾；结尾之后的下一个块边界继续找。
- 插件判为无效、超过最大尺寸，或到设备末尾仍不完整时，视为误识别，从它的下一块重新找，它覆盖过的块里可能有真正的文件。插件等待的位置已超出设备末尾或最大尺寸时，立即判为误识别。
- 没有结束标志的格式（PDF）遇到下一个文件头时收尾。
- 输出在指定目录下新建 `recovered-<任务 ID 前 8 位>` 子目录；文件名为 `f` 加十位起始扇区号（按 512 字节计），写入期间带 `.part` 后缀，确认完整后才改名。
- 读设备与识别在一个线程，写出交给单独的写线程，输出盘慢时扫描不必等它：
  - 识别线程把一个文件的数据攒到 1 MiB 再排进写队列；队列最多 32 条（在途数据约 32 MiB），排满时扫描等待（背压）；
  - 候选文件在第一次交出数据之前就被判为误识别时，输出盘上不建文件；
  - 写线程改好名才回报，「找到的文件」和恢复报告只计入已经改名的文件；取消或扫完时，先把队列里已确认完整的文件写完再结束，100% 进度在写完之后才报；
  - 写线程出错（例如输出盘满）时任务失败，报的是写线程的原始错误。
- 不逐个文件同步到盘：USB 机械盘上每次同步约 100 ms，攒一批再逐个同步也只省一半（每次同步都要让盘刷一次缓存），文件密集处会把扫描拖到每秒十来个文件；整卷一次同步要可写的卷句柄，引擎不具备写盘能力。改了名表示引擎确认文件完整、全部数据已交给操作系统：
  - 引擎崩溃、被结束或任务取消时不受影响，没写完的文件只留 `.part`；
  - 系统崩溃、断电或直接拔掉输出盘时，最近几秒改名的文件可能内容不全。源盘只读，重扫即可找回；拔输出盘前先在系统里安全移除。
- **输出不能写回被扫描的盘**：写出的文件会占用这块盘的空闲空间，而那正是还没找回的数据所在。源为物理磁盘时，引擎在创建任何输出目录之前核对（单是建目录就已经写到了盘上）：
  - 源盘的编号用 `IOCTL_STORAGE_GET_DEVICE_NUMBER` 查询；
  - 输出目录可能还不存在，取最近一级已存在的上级目录打开（随目录联接、符号链接走到真实位置），用 `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` 得到所在的卷，再用 `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 查出这个卷落在哪些盘上；还不存在的那几级目录之后才创建，不会改变所在的卷；
  - 卷只要有一段在源盘上就拒绝，答复 `OUTPUT_ON_SOURCE`；任何一项查不到（例如网络路径）同样拒绝，宁可不开始，也不冒险写回源盘；
  - 这些查询都以零访问权限进行，不需要特权，也不读磁盘内容；
  - 查不出的情况：输出在虚拟磁盘（VHD）上、而虚拟磁盘文件本身存放在源盘上时，查到的是虚拟磁盘自己的编号。
- 碎片重组、块大小探测、断点续传与流水线中的读线程（预读）在后续阶段加入；恢复报告目前只有按格式统计的数量与大小、读不出的字节数、用时和实际输出目录。

### 5.5 能力探测

`engine.capabilities` 返回引擎实际支持的文件系统、格式和操作。界面据此显示入口；暂不支持的功能显示原因，不显示为可点击。

### 5.6 能识别坏区的镜像

```
第 1 轮 复制   大块顺序读；遇错跳过一段（起步 64 KiB，连续出错时加倍，有上限），跳过的区段记入坏区图
第 2 轮 修边   对每个被跳过的区段，从两端按扇区向内读，碰到读错误就停
第 3 轮 细读   对剩下的未读区段逐扇区读一遍
第 4 轮 重试   只对仍然读不出的扇区按设定次数重试
```

- **坏区图**：记录每个区段的状态（未读、已读、待修边、待细读、坏），与镜像放在一起，是纯文本，随时落盘，中断后据此续做。
- **读取策略**：单次读超时、重试次数、跳过大小都可以配置。默认值偏保守，不对出错的盘反复施压；先把能读的读完，最后才碰坏区。
- **连接异常**：短时间内连续出错时暂停并提示检查连接。USB 通道重置也会表现成读错误，换线或换接口后可以续做。
- **输出**：镜像文件加坏区图。读不出的区域在镜像里填零，后续的检查和恢复按坏区图把它们当作"未知"，不当作真实的零。
- **进度**：当前轮次、已读字节、坏区字节、读速、剩余时间；扇区图实时标出各区段状态。

### 5.7 文件系统检查与修复（exFAT、FAT）

依据微软公开的 exFAT 与 FAT 文件系统规范实现。

| 阶段 | 只读检查的内容 |
|---|---|
| 引导区 | 主引导区与备份引导区是否一致；exFAT 引导校验和扇区；几何参数是否自洽 |
| 分配表 | FAT 链：越界、循环、交叉链接、提前结束 |
| 分配位图（exFAT） | 位图与实际占用逐簇比对 |
| 目录树 | 目录项集合的校验和、条目类型与次序、文件名哈希、长度与簇数是否相符；大写表 |
| 汇总 | 丢失簇（已占用但没有文件引用）、大小不符、坏簇标记 |

- **结果**：问题清单，按"会丢数据 / 结构错误 / 可以忽略"分级。每项列出位置、影响和可选修法，例如"截断到可读长度""另存为孤立文件""在 FAT 中标记为坏簇"。
- **修复**：用户勾选后，`repair.planFsFix` 生成写入计划（第 4.2 节），改前备份、改后读回校验、可回滚。默认先在镜像上修，确认结果后再决定是否写回原盘。
- **坏扇区**：检查只读元数据，不做整盘扫描，正常的盘几秒到几分钟就能查完。整盘坏区扫描由用户单独发起，与镜像共用读取策略。
- **进度**：阶段列表，加上本阶段的进度、已处理条目数、已发现的问题数；随时可以取消。
- **NTFS**：没有公开规范，只提供引导扇区与 MFT 镜像相关的检查和修复，不做全面修复。

## 6. 界面

### 6.1 场景向导

首页按任务组织，而不是按技术菜单：

1. 找回丢失的分区
2. 修复打不开的分区
3. 找回删除的文件
4. 按文件类型深度恢复
5. 检查并修复文件系统
6. 制作磁盘镜像（能识别坏区）

每个向导的步骤是：选择磁盘或镜像 → 分析 → 确认结果 → 执行 → 报告。任何向导在读到介质错误时，都会建议先转去制作镜像，再在镜像上继续。

已接入的是「按文件类型深度恢复」，其余场景暂时显示「引擎尚未接入」。首页与向导在同一页面里切换，不用路由；切换后焦点落在新视图的标题上。深度恢复向导分四步：

1. **来源**：镜像文件（路径框，或系统的选择文件对话框）或物理磁盘（与自检区共用磁盘列表）。
2. **格式**：列表来自 `carve.listFileTypes`，默认勾选各格式的默认设置；格式名按扩展名取本地化文案。
3. **保存位置**：系统的选择文件夹对话框，路径框也可以直接编辑。源为物理磁盘时提示输出必须在另一块盘上，开始时由引擎再核对一次（第 5.4 节）。
4. **开始**：进度与读速、按格式统计的已找到数量和大小、最近找到的文件，可以取消；结束后显示报告和实际输出目录。运行中不能返回上一步或首页。

读取扫描与深度恢复共用同一套任务状态（`useJob`：启动、取消、进度、无响应与恢复、终结），各自只处理自己的结果。

**专家模式**展开全部参数和实时日志，保证所有能力都有入口。

### 6.2 可视化

- 分区布局条：按比例显示分区、空闲区和找到的候选分区。
- 扫描扇区图：已扫描、已恢复、坏区分色显示；制作镜像时显示坏区图中各区段的状态。
- 检查结果：问题清单按严重程度分组，每项可以展开看位置、影响和修法。
- 恢复统计：按文件类型统计数量和大小。
- 写入前对比：修改前和修改后的分区表、引导扇区差异。

### 6.3 预览安全

恢复出的文件**不交给 WebView 直接渲染**。图片由引擎解码后生成缩略图；文本转义后以纯文本显示；其他类型只显示元数据和十六进制视图。恢复出的 HTML、SVG 等文件在 WebView 中会执行脚本。

### 6.4 其他

- 中文、英文两种界面语言。
- 浅色、深色主题；风险操作有固定的语义色。
- 全部操作可以只用键盘完成。
- 专业术语（CHS、引导扇区、MFT 镜像等）旁边给出解释。
- 大列表（十万级文件、深目录树）使用虚拟滚动。

## 7. 宿主

- 管理引擎进程与代理进程的启动、心跳、退出。引擎程序与宿主程序放在同一目录；Windows 上以 `CREATE_NO_WINDOW` 启动，不弹出控制台窗口。
- 把引擎事件合并后转给界面，界面侧不直接面对高频事件。界面只收一个事件 `job-event`，载荷是 `{jobId, kind, data}`，`kind` 为 progress、found、log、completed、failed、cancelled、unresponsive、responsive。
- 任务 ID 由界面生成（UUID），在调用启动命令之前就记下，避免事件先于命令返回到达时被丢掉；宿主只接受字母、数字和连字符。
- 返回给界面的错误是 `{code, detail}`：`code` 由界面翻译成当前语言，`detail` 是技术细节。引擎答复的错误码中，`SOURCE_UNAVAILABLE`、`OUTPUT_UNAVAILABLE`、`OUTPUT_ON_SOURCE` 分别转成 `sourceUnavailable`、`outputUnavailable`、`outputOnSource`，其余统一为 `engineRejected`。
- 磁盘代理在整个会话里只启动一次（第一次需要打开物理磁盘时），之后复用；宿主退出时代理随之退出。等待 UAC 期间，其他打开请求排队，不会同时弹出多个 UAC。代理程序同样放在宿主程序旁边，`tauri dev` / `tauri build` 会先编出引擎和代理。
- 本地保存任务记录，界面重启后可以看到历史任务并续传。
- Tauri 安全配置：严格 CSP；禁止加载远程内容；只开放白名单中的命令。系统文件对话框用官方的 dialog 插件，capability 只开放 `dialog:allow-open`（选择文件与文件夹）。

## 8. 质量目标的设计约束

| 目标 | 约束 |
|---|---|
| **高可用** | 进程隔离，引擎故障不影响界面；深度恢复和镜像都能断点续传；心跳与无响应处理；任务记录持久化；输出盘满自动暂停；连续读错误时暂停并提示检查连接 |
| **鲁棒** | 解析器对任意输入只返回结果或"不认识"，不 panic：禁用 `unwrap`/`expect`/直接下标，来自磁盘的数值一律用带检查的运算；panic 在任务边界捕获并转成任务失败；写入计划带前置哈希、备份、读回校验和回滚；磁盘报错时先镜像后修复，检查与修复分开 |
| **安全** | 解析代码不持有特权；引擎不具备写盘能力；默认只读，写盘必须进入修复模式；不监听端口；恢复文件不进 WebView；每个解析器都有 fuzz 目标；依赖经漏洞与合规检查；安装包签名 |
| **高性能** | 三段流水线；签名查找表；同盘顺序读、多盘并行；事件节流与批量合并；虚拟滚动；性能基准纳入持续集成 |
| **美观** | 统一的设计系统与主题；分区布局、扫描进度、恢复结果可视化 |
| **易用** | 场景向导；专家模式保留全部参数；写入前对比；双语；键盘可达；术语解释 |
