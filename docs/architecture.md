# 架构设计

## 1. 目标与范围

### 1.1 功能

| 场景 | 能力 |
|---|---|
| 分区恢复 | 读取并检查分区表；快速搜索与深度搜索丢失的分区；生成并写入新的分区表 |
| 分区修复 | 引导扇区检查、从备份恢复、重建（FAT、NTFS、exFAT、HFS/HFS+、ext 超级块）；FAT 表修复；NTFS MFT 从镜像修复；写入 MBR 引导代码 |
| 文件找回 | 浏览分区目录、复制文件、反删除（FAT、exFAT、NTFS、ext2/3/4） |
| 深度恢复 | 不依赖文件系统，按文件签名在整盘、分区或未分配空间中恢复数百种格式；块大小探测；暴力恢复；断点续传；恢复报告 |
| 文件系统检查与修复 | exFAT、FAT12/16/32 的完整一致性检查：引导区与校验和、FAT 链、分配位图、目录项集合与校验和、大写表，以及交叉链接、丢失簇、越界与循环链。先列出问题清单，用户勾选后生成修复计划；可标记坏簇，孤立的簇链可另存为文件。NTFS 只做有把握的部分（引导扇区、MFT 镜像） |
| 磁盘镜像 | 能识别坏区的镜像：首轮遇错跳过并记入坏区图，先读完完好区域，之后多轮缩小读取粒度回头重试；可暂停、断点续传；可以按分区多选、分几次做完，或者先只复制完好区域；坏区图随镜像保存。在镜像上可以执行以上全部操作 |

支持范围：

- **分区表**：MBR（含扩展分区）、GPT、Apple 分区图、Sun、Xbox、Humax、无分区表。
- **文件系统识别**：APFS、BeFS、BSD disklabel、Btrfs、CramFS、exFAT、ext2/3/4、FAT12/16/32、FATX、F2FS、JFS、GFS2、HFS、HFS+、HPFS、LUKS、LVM/LVM2、Linux RAID、NetWare NSS、NTFS、ReFS、ReiserFS、Sun、Linux Swap、System V、UFS/UFS2、VMFS、WBFS、XFS、ZFS。
- **镜像格式**：raw/dd、分段 raw、E01。
- **平台**：Windows 10/11、macOS、Linux 桌面。

### 1.2 质量目标

高可用、鲁棒、安全、高性能、美观、易用。每一项的设计约束见第 8 节。

### 1.3 数据安全原则

- **默认只读。** 所有写盘操作都先生成写入计划，经用户确认后执行（第 4.2 节）。
- **磁盘报读错误时，先镜像，后修复。** 一旦检测到介质错误，界面建议先制作镜像（第 5.6 节）；检查、修复、恢复都在镜像上进行，是否改动原盘由用户最后决定。对出错的盘反复读写会加重损坏。
- **检查与修复分开。** 检查阶段只读，随时可以取消；修复只处理用户勾选的问题，并且改前备份、改后读回校验。

## 2. 总体架构

```
┌──────────────────── 界面进程（普通权限）────────────────────┐
│  Tauri 2 宿主（Rust）  ⇄  界面（Vue 3 + TypeScript）         │
│  任务管理 · 进程守护 · 事件节流 · 本地任务记录               │
└──────────────┬──────────────────────────────┬──────────────┘
               │ JSON-RPC（stdio 管道）        │ JSON-RPC（管道，见 4.1）
┌──────────────▼──────────────────┐  ┌────────▼──────────────────────┐
│ 引擎进程（每个任务一个，普通权限）│  │ 磁盘代理（特权，代码最少）      │
│  engine   任务 / 决策 / 进度 / 取消│◄─┤  打开设备，把只读句柄交给引擎   │
│  repair   分区恢复与修复          │  │  执行写入计划                   │
│  carve    深度恢复                │  │                                 │
│  formats  文件格式插件            │  └───────────────────────────────┘
│  fs       文件系统                │
│  part     分区表                  │
│  io       块设备 / 镜像 / 缓存     │
└─────────────────────────────────┘
```

拆成三类进程的原因：

1. **解析不可信数据的代码不持有特权。** 磁盘内容可能已损坏，也可能被刻意构造。所有解析都在普通权限的引擎进程里进行，即使解析器有缺陷，也拿不到写盘或提权的能力。
2. **故障隔离。** 引擎崩溃、陷入死循环或内存失控，只影响这一个任务；界面会报告原因，可以重试或从断点续传。
3. **特权代码最少、可审查。** 只有磁盘代理持有特权，它只做两件事：打开设备、执行写入计划。列出磁盘只需查询设备属性，由引擎以普通权限完成（第 4.1 节）。
4. **桌面环境限制。** 不少 Linux 桌面（Wayland）默认不允许 root 进程直接开窗口，界面本来就不能以特权身份运行。

宿主与引擎之间走父子进程的 stdio 管道。宿主与磁盘代理之间：Linux 同样走 stdio；Windows 上提权进程接管不了 stdio，改走命名管道（第 4.1 节）。都不监听任何网络端口。

## 3. 进程与通信

### 3.1 协议

- JSON-RPC 2.0，每条消息前加 4 字节小端长度成帧，单条消息不超过 1 MiB。成帧与消息类型在 `yisi-rpc`，宿主、引擎、代理共用。
- 宿主 → 引擎：请求（启动任务、回答决策、取消）。启动任务的请求带上任务 ID（由界面生成），引擎立即答复空对象，之后的进展都以通知送达。
- 引擎 → 宿主：答复，以及不带 id 的通知：`engine.heartbeat`、`job.progress`、`job.log`、`job.completed`、`job.failed`、`job.cancelled`，`job.found`（深度恢复找到的文件）、`job.copied`（复制好的文件）、`job.imaging`（制作镜像的进展：当前轮次、本次范围内已读与读不出的字节数、各类待读的字节数、最近几秒的读速，每秒最多 5 次），`job.reading`（任务读源的累计统计：读取次数、字节数、读错次数、单次超过 2 秒的读取次数、读取总用时、此刻已经卡了多久，任务运行期间每秒一次、没有变化时不发；见第 5.2 节），以及之后的 `job.decision`。每条任务通知都带 `jobId`。
- `job.progress` 在引擎侧节流，每秒最多 10 次，完成那一次总会发出；有几个阶段的任务带 `stage`（浏览与复制的 `scanMft`：扫描 MFT，单位是字节；制作镜像的轮次；文件系统检查的 `boot`、`fat`、`directories`、`clusters`、`mft`，见第 5.7 节）。`found` 事件批量合并后发出。
- 方法名、参数与结果的类型定义在 `yisi-engine` 的库部分（`protocol`），宿主直接引用，不另写一份。

### 3.2 任务生命周期

```
created → running ⇄ waiting_decision → completed
                 ↘ cancelling → cancelled
                 ↘ failed
```

- 每个任务一个引擎进程，任务结束后进程退出。宿主断开（引擎的 stdin 结束）时，引擎取消正在运行的任务后退出。
- 界面页面开始（重新）加载时（按 F5、开发时整页重载），宿主取消全部正在运行的任务：新页面不认得旧页面发起的任务，留着只会一直占着源盘。
- 取消：先发 `job.cancel`，引擎在下一个检查点结束任务并发出 `job.cancelled`；5 秒内未退出时，宿主结束进程，仍按取消处理。
- 暂停与继续：`job.pause` / `job.resume`，任务在下一个检查点停下等待，取消（包括宿主断开）会把它放行。目前深度恢复的扫描、丢失分区搜索与文件系统检查可以暂停。深度恢复：识别线程每处理一块过一次闸门，读线程预读满队列（4 段）后也停下，所以暂停期间不读盘。丢失分区搜索每读 1 MiB 过一次闸门。文件系统检查是单线程顺序读，每查一个目录、FAT 与逐簇汇总每 65536 簇过一次闸门。报告的用时都扣掉暂停的时长。其他任务收到暂停答复 `INVALID_PARAMS`。暂停期间心跳照常，宿主不会把它当成无响应。
- 任务里的 panic 在任务边界捕获，转成 `job.failed`；引擎没有发出终结通知就退出时，宿主按失败处理并带上退出码。
- 心跳：引擎每 2 秒发一次心跳；超过 10 秒没有心跳，标记为无响应，由用户决定等待还是结束；心跳恢复后撤销标记。
- 资源上限：引擎进程设置内存上限（Windows 用作业对象，Linux/macOS 用 rlimit）。

### 3.3 决策事件

恢复流程中需要用户判断的地方（确认写入、选择分区、输入参数等），以决策事件发给界面。引擎阻塞等待答复，流程代码保持顺序写法。

```json
{"type":"decision","jobId":"j1","id":"d7","kind":"confirm","risk":"write",
 "title":"写入分区表","detail":{"before":[...],"after":[...]},
 "options":["apply","cancel"],"default":"cancel"}
```

- `kind`：`confirm`、`select`、`number`、`text`、`location`。
- **`risk` 为 `write` 的决策，默认值固定为取消；等待超时也按取消处理。**

### 3.4 RPC 方法（初版）

| `repair.analyse` | 读取当前分区表并检查结构 |
| `repair.search` | 搜索丢失的分区（任务，只读，可以暂停）：从头到尾读一遍源，找出 FAT、exFAT、NTFS 的引导扇区（含备份）并核对结构，结果是候选分区（起点、长度、文件系统、卷标、靠主引导扇区还是备份找到、与现有分区表的关系）与读不出的字节数（第 5.9 节） |

| `repair.openRange` | 在浏览会话里按位置打开一个不在分区表里的分区（搜索找到的）：参数是起点、长度与 `boot`（只靠备份引导扇区找到的分区为 `backup`，与 `repair.open` 的同名参数一样按备份打开），答复分区信息，编号从 100000 起，之后与表里的分区一样列目录、预览、扫描。同一位置再打开答复同一编号；范围超出源时答复 `INVALID_PARAMS`（第 5.9 节） |
| `repair.scanDeleted` / `repair.cancelScan` | 找出浏览中的一个分区里已删除的项：NTFS 扫一遍 MFT，期间浏览任务发 `job.progress`（`stage` 为 `scanMft`），扫完答复记录数、已删除数、找不到原目录的数；扫过的分区直接答复上次的结果，其他文件系统立即答复。`repair.cancelScan` 停下正在进行的扫描，那次扫描答复 `cancelled` |
| `repair.listFiles` / `repair.previewFile` | 列出浏览中的一个目录的一页（含已删除的项与可信度）；预览其中一个文件，规则同 `preview.file`。分区或定位信息不对时答复 `FS_UNAVAILABLE` |
| `repair.copyFiles` | 把选中的文件与目录复制到另一块盘（任务），已删除的项同样可以复制（反删除）；NTFS 分区上选了目录时先扫一遍 MFT（进度带 `stage`）。复制好的文件经 `job.copied` 分批通知。源为物理磁盘时规则同 `carve.start`。`boot` 与浏览时一致；按位置打开的分区（编号从 100000 起，只看编号这一个判据）引擎不核对分区表，只核对范围在源之内（与「检查文件系统」核对分区用同一个函数） |
| `repair.planPartitionWrite` / `repair.planBootSector` / `repair.planFatRepair` / `repair.planMftRepair` | 只生成写入计划，不写盘 |

| `broker.openDisk` | 磁盘代理以只读方式打开物理磁盘，把句柄复制进指定的引擎进程（第 4.1 节） |
| `broker.executeWrite` | 由磁盘代理执行一份已确认的写入计划 |
| `broker.shutdown` | 结束磁盘代理 |
| `carve.listFileTypes` | 列出全部格式和分组 |
| `carve.start` / `carve.resume` | 启动或续传深度恢复（任务）；接下任务时答复实际输出目录，找到的文件经 `job.found` 分批通知。给了输出目录时边扫边保存，源为物理磁盘时输出目录必须在另一块盘上，否则答复 `OUTPUT_ON_SOURCE`（第 5.4 节）；不给时只扫描、什么都不写，答复的输出目录为空 |

| `preview.range` | 预览源上的一段（只扫描、还没保存的文件），规则同 `preview.file` |
| `preview.file` | 预览一个文件：长度、开头 4 KiB；JPEG、PNG 另给缩略图（第 6.3 节）。打不开时答复 `PREVIEW_UNAVAILABLE` |
| `image.create` / `image.resume` | 制作或续做能识别坏区的镜像（任务）：参数是源与镜像文件的完整路径（坏区图是同一路径加 `.map`），以及可选的 `ranges`（只读这些范围，不给时读整个源）、`copyOnly`（只做复制这一轮）、`reset`（开始前把这些范围的进度清掉、重新读）。建好或打开这两个文件后答复它们的路径，进展经 `job.progress`（`stage` 为轮次）与 `job.imaging` 送达，结果是读出、读不出的字节数与读不出的区段（最多 1000 段）。新建时镜像或坏区图已存在答复 `IMAGE_EXISTS`；续做时坏区图不存在、读不懂，或记录的容量、扇区大小、来源与当前的源不符，答复 `IMAGE_MISMATCH`；源为物理磁盘时规则同 `carve.start`（`OUTPUT_ON_SOURCE`），源为镜像文件时不能写到来源文件自己上。只读一部分而镜像不是稀疏文件时答复 `INVALID_PARAMS`，稀疏镜像所在的盘放不下这一次最多要写的量时答复 `OUTPUT_UNAVAILABLE`。取消时保存坏区图，之后续做（第 5.6 节） |
| `image.inspect` | 做镜像之前看一眼（只读，读完即答复，不是任务）：源上现在的分区（与浏览时一样）与分区以外的空隙各做到哪了、只读一部分时总会一起读的分区表区域、输出位置所在卷的文件系统、是否支持稀疏文件与剩余空间；这个位置已有镜像时，它能不能续做（坏区图在不在、读不读得懂、是不是这个源做的、镜像长度对不对、是不是稀疏文件）、与上次开始读时相比分区表的变化，以及抽查结果（第 5.6 节）。镜像在源盘上时答复 `OUTPUT_ON_SOURCE` |
| `image.describe` | 查看以前做过的镜像现在怎样（只读坏区图，不碰源）：每个路径给出 ok、missing（镜像与坏区图都不在了）、imageMissing、mapMissing、mapUnreadable 之一，以及来源标识、容量、整个源的进展、坏区图最后保存的时间 |
| `disk.readScan` | 从头到尾顺序读一遍设备或镜像，记下读不出的区段（任务，只读）；整盘坏区扫描的基础 |
| `job.cancel` / `job.status` | 取消任务；查询状态 |
| `job.pause` / `job.resume` | 暂停、继续任务（目前只有 `carve.start`、`repair.search` 与 `fs.check`），见第 3.2 节 |

## 4. 特权与设备访问

### 4.1 只读句柄传递

磁盘代理以特权打开设备，把**只读**句柄交给引擎：

| 平台 | 提权方式 | 句柄传递 |
|---|---|---|
| Linux | polkit（pkexec）启动代理 | Unix 套接字 `SCM_RIGHTS` |
| macOS | 系统授权服务 | 与 `authopen` 相同的描述符传递方式 |
| Windows | 代理以管理员身份运行（UAC） | `DuplicateHandle` 复制到引擎进程 |

引擎侧的块设备类型**不提供写方法**，写盘能力在类型层面就不存在于引擎中。

**Windows 的做法。** 普通权限的宿主只能用 `ShellExecuteEx("runas")` 启动提权进程，接管不了它的 stdio，所以宿主与代理之间走命名管道：

- 管道由宿主创建，名字带 128 位随机数；`FILE_FLAG_FIRST_PIPE_INSTANCE` 让抢先占用同名管道的情况直接失败，`PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程连接。
- 管道的 ACL 只允许管理员组和 SYSTEM。提权后的代理属于管理员组；未提权的进程，即使与宿主是同一用户，也连不上。
- 双向核对身份：宿主核对连进来的客户端进程就是刚启动的代理；代理核对管道的服务端进程就是命令行给出的宿主。
- 宿主退出时代理随之退出，管道关闭时代理读到结束后退出，不留下以管理员身份运行的孤儿进程。
- 代理只接受 `\\.\PhysicalDriveN`（N 为一到三位数字）与卷 `\\.\C:`（一个大写字母加冒号）两种路径，不替宿主打开任意文件。路径规则只有一份（`yisi_io::physical_drive_path` / `physical_drive_number`、`volume_path` / `volume_letter`），列出磁盘、宿主拼路径、代理核对都用它。卷与物理盘一样以只读、共享读写的方式打开，引擎同样用 `WindowsDisk` 认领（卷的句柄也能回答容量、几何与设备编号的查询），整个卷当作没有分区表的源。
- 代理只读打开设备，用 `DuplicateHandle(…, DUPLICATE_SAME_ACCESS)` 复制进引擎进程，复制出的句柄与原句柄一样只有读权限（实测授予的权限为 `FILE_GENERIC_READ`）。
- 引擎用 `WindowsDisk::adopt_handle` 认领句柄：只接受能回答磁盘 IOCTL 的句柄，同一个值只能认领一次。引擎自己没有权限打开磁盘，这类句柄只能来自代理。

macOS 的特权辅助程序同样没有 stdio，通道在实现 macOS 版时确定（XPC）。

**列出磁盘不需要特权。** Windows 允许普通权限以零访问权限打开 `\\.\PhysicalDriveN`，只查询设备属性、不读写内容：容量与逻辑扇区大小用 `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX`，厂商、型号、序列号、总线与是否可移动用 `IOCTL_STORAGE_QUERY_PROPERTY`（同一个查询换成寻道开销属性得出固态或机械），分区表格式用 `IOCTL_DISK_GET_DRIVE_LAYOUT_EX`。盘符与卷向系统查（`yisi_io::mounted_volumes`：`GetLogicalDrives` 列出盘符，只看本机硬盘与可移动盘，卷属性与 `image.inspect` 查输出位置共用 `volume_info`，卷所在的磁盘用卷的磁盘区段查询），与资源管理器显示容量的方式相同。所以 `disk.list` 由引擎完成，用户选好盘、真正要读的时候才需要代理。

**扫描一块物理磁盘的流程（Windows）：**

1. 宿主启动引擎，得到它的进程 ID；
2. 宿主确保代理在运行：第一次需要时提权启动（弹 UAC），之后整个会话复用；代理通信失败时丢掉连接，下次重新启动；
3. 代理只读打开磁盘，把句柄复制进这个引擎；
4. 宿主向引擎发起任务，源为 `{type: "disk", handle}`，引擎用 `WindowsDisk::adopt_handle` 认领后照常读取。

### 4.2 写入计划

所有写盘操作都先由引擎生成写入计划，经用户确认后交给代理执行：

```rust
pub struct WritePlan {
    pub id: PlanId,
    pub device: DeviceIdentity,      // 序列号、容量、扇区大小，防止写错盘
    pub writes: Vec<SectorWrite>,    // 起始扇区、新内容、写前内容的 SHA-256
    pub summary: PlanSummary,        // 给界面展示的修改前后对比
}
```

代理按以下步骤执行，任何一步失败都停止，并报告停在哪一步：

1. 核对设备身份与计划一致；
2. 读取目标扇区，核对写前哈希。不一致说明磁盘在计划生成后被改动过，拒绝执行；
3. 把原扇区内容和元数据写入备份文件；
4. 写入并刷盘；
5. 读回校验；
6. 记录执行结果。

回滚就是把备份文件当成一份新的写入计划执行。

## 5. 引擎模块

### 5.1 模块与依赖方向

```
io ← part ← fs ← repair ─┐
          ↖ formats ← carve ├─ engine
                          ┘
io ← broker
rpc ← engine、broker、宿主（宿主另外引用 engine、broker 的库部分）
```

| 目录 | 包名 | 职责 |
|---|---|---|
| `crates/io` | `yisi-io` | 块设备抽象；Windows/macOS/Linux 后端；raw、分段 raw、E01；读缓存；坏扇区读取策略；能识别坏区的镜像（第 5.6 节）；从头到尾顺序读一遍设备（`scan_device`，读取扫描与丢失分区搜索共用）；物理磁盘路径规则；输出不在源盘上的判断 |
| `crates/part` | `yisi-part` | 分区表的解析、校验、序列化与自动识别；CRC-32（GPT 与 PNG 共用）；按偏移取大端、小端整数（`bytes`，各 crate 共用） |
| `crates/fs` | `yisi-fs` | 文件系统识别；目录读取（含已删除的项）与文件提取（第 5.8 节）；找备份引导扇区、按备份打开卷（第 5.10 节）；空闲空间位图；引导扇区与超级块的检查和重建 |
| `crates/formats` | `yisi-formats` | 文件格式插件与注册表 |
| `crates/carve` | `yisi-carve` | 深度恢复：搜索空间、块大小探测、识别分派、数据检查、暴力恢复、断点续传、恢复报告 |
| `crates/repair` | `yisi-repair` | 分区分析与搜索、结构检查（引导扇区诊断，第 5.10 节）、反删除；文件系统一致性检查（`check`：exFAT / FAT 完整检查、NTFS 少数几项，只读，输出问题清单，第 5.7 节）；生成写入计划（分区表、引导扇区、FAT/MFT 修复、文件系统修复） |
| `crates/engine` | `yisi-engine` | 引擎进程入口：任务运行时、决策事件、进度节流、取消。库部分只有宿主与引擎之间的方法与参数（`protocol`），供宿主引用 |
| `crates/broker` | `yisi-broker` | 磁盘代理。库部分供宿主使用：方法与参数、Windows 上建管道和提权启动；程序部分是以管理员身份运行的代理本身 |
| `crates/rpc` | `yisi-rpc` | 成帧与 JSON-RPC 2.0 消息；把错误及其来源串成一句话（`error_chain`）；宿主、引擎、代理共用 |

`formats` 只用 `part` 里的 CRC-32 与字节读取。目前「找回删除的文件」只读，引擎直接调用 `part` 与 `fs`。`repair` 里有引导扇区诊断（第 5.10 节）、丢失分区搜索（第 5.9 节）与文件系统检查（第 5.7 节），都只读；文件系统检查不经过 `fs` 打开卷：检查要逐项读出损坏的结构并说清是哪一项坏了，`fs` 遇到不自洽的结构只会拒绝打开；但判读同一个字节的规则用 `fs` 里的同一份：引导扇区参数的核对与主备要一致的字段（`bpb`，第 5.10 节）、备份引导扇区的位置与认法（`boot`）、FAT 表项的位置与含义、介质描述符、目录项的首簇、长文件名、exFAT 目录项集合（`format`）、`$MFT` 自身记录可不可用（`mft_self_record_ok`）、exFAT 引导区校验和、FAT 短文件名的校验和与显示形式。写入计划以后再加。

**unsafe 边界**：只有 `io` 和 `broker` 允许 `unsafe`，用于平台系统调用，每处都要写清安全性论证；其余模块一律 `#![forbid(unsafe_code)]`。

### 5.2 块设备抽象

```rust
pub trait BlockDevice: Send + Sync {
    fn size(&self) -> u64;
    fn sector_size(&self) -> u32;
    fn read_at(&self, offset: u64, buf: &mut [u8]) -> Result<usize, IoError>;
    fn read_exact_at(&self, offset: u64, buf: &mut [u8]) -> Result<(), IoError>; // 有默认实现
}
```

- `read_at` 的偏移和长度不要求按扇区对齐；读到设备末尾时截断，偏移不小于容量时返回 0。`read_exact_at` 读不满时返回带偏移的错误，供解析器使用。
- 物理盘只接受起点、长度、缓冲区地址都按扇区对齐的读请求。后端在内部处理：请求本身已经对齐时直接读进调用方的缓冲区，否则经对齐的中转缓冲区（每次最多 1 MiB）读取再拷贝。
- Windows 后端以只读、共享读写的方式打开 `\\.\PhysicalDriveN`，不加锁、不独占；容量和逻辑扇区大小用 IOCTL 查询。
- 镜像文件不记录扇区大小，打开时由调用方给出（取来源磁盘的逻辑扇区大小）。扇区大小只接受 512 到 64 KiB 之间的 2 的幂。
- 读错误带上偏移和系统错误码，供坏区策略识别介质错误。
- 读错误按策略处理：重试次数、超时、跳过并记入坏区表，都可以配置。
- 读缓存按扇区对齐；镜像文件优先用内存映射。
- **读取统计**：引擎打开的源一律经读取计数器（`yisi_io::MeteredDevice` / `ReadMeter`）读，记下读取次数、字节数、读错次数、单次超过 2 秒的读取次数（`SLOW_READ`，盘在内部反复重试）、读取总用时，以及此刻已经连续读了多久还没读完。每个引擎进程只运行一个任务，计数器整个进程一份（引擎 `reading`），任务运行期间每秒把从任务开始算的累计统计经 `job.reading` 发出。界面据此判断读得慢的原因（第 6.1 节）。

### 5.3 文件格式插件

```rust
pub trait FileFormat: Send + Sync {
    fn info(&self) -> &FormatInfo;          // 扩展名、描述、最大尺寸、默认启用
    fn signatures(&self) -> &[Signature];   // (偏移, 魔数)
    fn header_check(&self, block: &[u8]) -> Option<Box<dyn Recovering>>;
}

pub trait Recovering: Send {
    fn data_check(&mut self, offset: u64, block: &[u8]) -> DataCheck; // 继续 / 在某长度处结束 / 无效
    fn open_ended(&self) -> bool;                // 没有结束标志（如 PDF）：遇到下一个文件头时收尾
    fn finish(&mut self, received: u64) -> Option<u64>; // 数据到此为止时的文件长度
    fn waiting_at(&self) -> Option<u64>;         // 正在等待的位置，用来尽早排除长度离谱的误识别
}
```

- **结构遍历器**：大多数格式的插件只实现一个小状态机，每一步告诉遍历器「下一步要从哪里开始的几个字节」（`Need`）、「从哪里开始找什么」（`Scan`）、「文件在这里结束」（`Done`）或「无效」。跨块拼接、跳过大段数据、跨块查找都由遍历器处理，插件不必关心数据怎么分块。遍历器保留最近一次交付或匹配处的字节，插件可以先读签名、再从同一位置读整条记录。
- 一个格式一个源文件，自带样本测试。样本由代码按格式结构现场生成（`yisi-formats` 的 `test-samples` 特性），不放二进制样本进仓库；每个格式还要过同一组随机与变异输入测试，只能给出结果或「不认识」，不能 panic。
- 插件只在能确认文件完整时给出长度，被截短的文件判为不完整、不输出（目前没有「部分恢复」）。没有结束标志的格式要从结构里找证据，例如 MP4（ISO/IEC 14496-12）：
  - 在不认识的顶层 box 处或数据结束处收尾，此前要见过 `moov` 和 `mdat`；
  - 分片文件的 `sidx` 登记了索引内容的长度：sidx 结尾 + `first_offset` + 各条 `referenced_size` 之和（版本 0 为 32 位、版本 1 为 64 位字段），文件至少要到这里，有多个 `sidx` 时取最大值；之后还可以有 `mfra` 等 box；
  - 最后一个 box 不能是 `moof`：它的样本在紧随其后的 `mdat` 里；
  - 看不出的情况：没有 `sidx` 的分片文件正好在一组 `moof` + `mdat` 之后截断；`sidx` 放在单独的索引文件里（以 `styp` 开头，本来就不会被 `ftyp` 签名命中）。
- 注册表在启动时把全部签名建成「偏移 + 前两个字节」的查找表，每个块只查表，不遍历格式。
- 界面上的格式列表来自 `carve.listFileTypes`，不在界面里硬编码。
- 按内容给文件命名（`rename`）在后续加入。

### 5.4 深度恢复流水线

```
读线程 ──(块环形缓冲)──▶ 恢复线程 ──(输出队列，带背压)──▶ 写线程
大块、对齐、顺序读         查签名表、跑格式状态机          写出恢复文件
预读                       维护搜索空间                    检查输出盘空间
```

- 同一块物理盘只有一条顺序读流，避免磁头来回寻道，也减轻对故障盘的压力。
- 读盘、计算、写出三者并行。
- 不同物理盘的任务各开一个引擎进程，可以并行。
- 输出盘空间不足时自动暂停并通知界面。
- 定期写入断点，异常退出后可以续传。

**目前的实现（线性恢复，只处理连续存放的文件）：**

- 按 1 MiB 读设备，再按扇区大小的块处理；文件只可能从块边界开始。整段读不出时逐块重读，只跳过真正读不出的块，正在恢复的文件随之放弃。
- 块开头命中文件头时开始恢复，后续块交给插件判断结尾；结尾之后的下一个块边界继续找。
- 插件判为无效、超过最大尺寸，或到设备末尾仍不完整时，视为误识别，从它的下一块重新找，它覆盖过的块里可能有真正的文件。插件等待的位置已超出设备末尾或最大尺寸时，立即判为误识别。
- 没有结束标志的格式（PDF）遇到下一个文件头时收尾。
- 输出在指定目录下新建 `recovered-<任务 ID 前 8 位>` 子目录；文件名为 `f` 加十位起始扇区号（按 512 字节计），写入期间带 `.part` 后缀，确认完整后才改名。
- **先只扫描、扫完再保存**：`carve.start` 不给输出目录时，写出端换成什么都不写的一个，识别流程完全一样，只记下每个文件在源上的位置、长度和格式，也不需要核对输出盘。保存选中的文件（`carve.extract`）时，把源上每个文件所在的那一段当作一块小设备，只启用它的格式再跑一遍深度恢复：保存时因此重做一遍格式校验，找到的文件起点、长度与扫描时一致才保留，源上的内容在扫描后变了的不保存、报告原因。代价是保存时要再读一次源（只读选中的部分）；扫描结果只在内存里，离开前要保存。
  - 文件直接存进用户选的目录，不另建子目录：先在目录里新建的暂存子目录（`.yisi-saving-<任务 ID 前 8 位>`，必须是新建的）中恢复、校验，通过的再改名移到目录下，任务结束时删掉暂存子目录；
  - 名字用另存为时给的（引擎替换掉系统不允许的字符），不给时按在源上的位置起，与边扫边保存时一样；与目录里已有的文件重名时加「 (1)」这样的序号，不覆盖；
  - 为「打开」「复制」先存一份副本时，宿主把输出目录定在程序目录下的 `open-cache\<任务 ID>`，同时在后台线程里删掉 `open-cache` 下其他的子目录（跳过还在运行的任务；删不掉的，例如还开着的，留到下一次），不拖慢这一次保存。程序目录在被扫描的盘上或写不进去时，引擎照常拒绝，界面改为请用户选保存位置。
- 上面的三段流水线已经实现：读线程顺序读设备，识别在调用线程里进行，写出交给写线程，读盘、识别、写盘同时进行。
  - 读线程按 1 MiB 一段读，最多领先识别 4 段；用完的缓冲区还给读线程重复使用。识别要回头重找（误识别后从它的下一块重找）时，请读线程从新位置重读，队列里旧位置的段丢掉。整段读不出时逐块重读，只标出真正读不出的块（同上）。读线程只会因程序缺陷 panic，这时识别线程把 panic 原样续抛，不会把后面的盘都当成读不出；
  - 0 号盘（NVMe，只读扫描约 1.5 GiB/s）只勾 PDF、1→8.5 GiB 之间没有写出：读与识别在同一线程时 1177–1276 MiB/s（4 次均值 1232），读线程上线后 1159–1403 MiB/s（4 次均值 1314），平均约快 7%，波动与差值同一量级；
  - 识别线程把一个文件的数据攒到 1 MiB 再排进写队列；队列最多 32 条（在途数据约 32 MiB），排满时扫描等待（背压）；
  - 候选文件在第一次交出数据之前就被判为误识别时，输出盘上不建文件；
  - 写线程改好名才回报，「找到的文件」和恢复报告只计入已经改名的文件；取消或扫完时，先把队列里已确认完整的文件写完再结束，100% 进度在写完之后才报；
  - 写线程出错（例如输出盘满）时任务失败，报的是写线程的原始错误。
- 不逐个文件同步到盘：USB 机械盘上每次同步约 100 ms，攒一批再逐个同步也只省一半（每次同步都要让盘刷一次缓存），文件密集处会把扫描拖到每秒十来个文件；整卷一次同步要可写的卷句柄，引擎不具备写盘能力。改了名表示引擎确认文件完整、全部数据已交给操作系统：
  - 引擎崩溃、被结束或任务取消时不受影响，没写完的文件只留 `.part`；
  - 系统崩溃、断电或直接拔掉输出盘时，最近几秒改名的文件可能内容不全。源盘只读，重扫即可找回；拔输出盘前先在系统里安全移除。
- **输出不能写回被扫描的盘**：写出的文件会占用这块盘的空闲空间，而那正是还没找回的数据所在。源为物理磁盘时，引擎在创建任何输出目录之前核对（单是建目录就已经写到了盘上）：
  - 源盘的编号用 `IOCTL_STORAGE_GET_DEVICE_NUMBER` 查询；
  - 输出位置可能还不存在，取最近一级已存在的文件或目录打开（随目录联接、符号链接走到真实位置），用 `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` 得到所在的卷，再用 `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 查出这个卷落在哪些盘上；还不存在的那几级目录之后才创建，不会改变所在的卷；
  - 卷只要有一段在源盘上就拒绝，答复 `OUTPUT_ON_SOURCE`；任何一项查不到（例如网络路径）同样拒绝，宁可不开始，也不冒险写回源盘；
  - 源是一个卷（盘符）时只看卷：输出所在的卷（`yisi_io::volume_guid`，卷的 GUID 名，按上一条的同一套办法取，所以输出是指向别的卷的符号链接时，两项检查看的是同一个卷；`image.inspect` 与制作镜像查输出卷的文件系统、是否支持稀疏、剩余空间的 `yisi_io::volume_info` 也按这个卷的 GUID 根路径查）不能就是源卷，同一块盘上的别的卷可以（写在那里不会覆盖源卷的空闲空间），规则是 `yisi_io::ensure_off_volume`；
  - 这些查询都以零访问权限进行，不需要特权，也不读磁盘内容；
  - 查不出的情况：输出在虚拟磁盘（VHD）上、而虚拟磁盘文件本身存放在源盘上时，查到的是虚拟磁盘自己的编号。
- 碎片重组、块大小探测、断点续传在后续阶段加入；恢复报告目前只有按格式统计的数量与大小、读不出的字节数、用时和实际输出目录。

### 5.5 能力探测

`engine.capabilities` 返回引擎实际支持的文件系统、格式和操作。界面据此显示入口；暂不支持的功能显示原因，不显示为可点击。

### 5.6 能识别坏区的镜像

```
第 1 轮 复制   大块顺序读；遇错跳过一段（起步 64 KiB，连续出错时加倍，有上限），跳过的区段记入坏区图
第 2 轮 修边   对每个被跳过的区段，从两端按扇区向内读，碰到读错误就停
第 3 轮 细读   对剩下的未读区段逐扇区读一遍
第 4 轮 重试   只对仍然读不出的扇区按设定次数重试
```

- **坏区图**：记录每个区段的状态（未读、已读、待修边、待细读、坏），与镜像放在一起，是纯文本，随时落盘，中断后据此续做。
- **读取策略**：单次读超时、重试次数、跳过大小都可以配置。默认值偏保守，不对出错的盘反复施压；先把能读的读完，最后才碰坏区。
- **连接异常**：短时间内连续出错时暂停并提示检查连接。USB 通道重置也会表现成读错误，换线或换接口后可以续做。
- **输出**：镜像文件加坏区图。读不出的区域在镜像里填零，后续的检查和恢复按坏区图把它们当作"未知"，不当作真实的零。
- **进度**：当前轮次、已读字节、坏区字节、读速、剩余时间；扇区图实时标出各区段状态。

**目前的实现（第 1–3 轮）：**

- 读取策略与坏区图在 `yisi-io` 的 `imaging`，只管读和记；镜像与坏区图怎样落盘由调用方实现（引擎的 `image_job` 写文件，单元测试写内存）。
- **第 1 轮复制**分三遍，读错的块都记为待修边：
  - 正向按 1 MiB 读还没读过的区段；读错后跳过一段，起步 64 KiB，连续出错时加倍，上限是容量的 1/1024（在 64 KiB 到 1 GiB 之间），读成功一次就回到起步值。被跳过的区段仍记为未读；
  - 反向从远端往回读被跳过的区段，同样遇错跳过：碰到坏区时是从完好的一侧靠近它；
  - 最后正向不跳过地补读剩下的未读区段。之后不再有未读的区段。
- **第 2 轮修边**：每个待修边的区段从前往后按扇区读到第一个读错的扇区（记为坏），再从后往前读到第一个读错的扇区（记为坏），中间剩下的记为待细读。读错的那个扇区已经单独读过，细读不再碰它，每个坏扇区只被单独读一次。
- **第 3 轮细读**：待细读的区段逐扇区读一遍，读不出的记为坏。
- **只读一部分**（`yisi_io::Scope`）：一次运行可以只读几个范围（选中的分区或空隙），三轮都只在范围之内找要读的区段；坏区图始终覆盖整个设备，范围以外原样留着，下次换个范围或不加限制再做时接着读。范围的起点向下、终点向上对齐到扇区，重叠或相接的合并。只读一部分时引擎另外加上分区表区域：开头与末尾各 1 MiB（MBR、GPT 与它的备份）与每个分区之前的 1 MiB（逻辑分区的链表项在它前面），都只取不属于任何分区的部分（`image_job::table_areas`），之后在镜像上才认得出分区。没有分区表（整个源是一个文件系统）时不另加。
- **先只复制完好区域**（`copyOnly`）：第 1 轮只做正向与反向两遍，不做「不跳过地补读」，也不做修边与细读；读错的块（坏区附近约 1 MiB）与跳过的区段留到以后，进度按「过了一遍」计。之后不加这个选项再做，照常补完。
- **重做**（`reset`）：开始前把给出的范围设回未读，用于重做做完的分区，或者源在做镜像之后变过的部分。
- 第 4 轮重试、单次读超时、可调的读取参数、暂停（现在「停止」就是存好坏区图后结束，之后续做）和扇区图在后续加入。
- **坏区图格式**（UTF-8 文本，`#` 开头的是注释）：

  ```
  version 2
  size 1000204886016
  sector 512
  source disk WDC WD10EZEX-08WN4A0 WD-WCC6Y0123456
  part 1 1048576 524288000
  part 2 525336576 999678459904
  0 2469203456 done
  2469203456 512 bad
  2469203968 997735682048 untried
  ```

  头部是格式版本、容量、扇区大小与来源标识（物理盘是厂商、型号、序列号，不含会随插拔变化的磁盘编号，与 `disk.list` 给出的 `identity` 相同；镜像文件是规范化后的路径），版本 2 起再记最近一次开始读时源上的分区表（`part 编号 起点 长度`，版本 1 没有这些行，照样能读），之后每行一个区段「起始偏移 长度 状态」，状态是 `untried`、`done`、`trim`、`scrape`、`bad`，相邻的同状态区段合并。读回时区段必须首尾相接、覆盖整个设备、状态都认识，否则不续做：坏区图决定哪些位置不再读，宁可不续做，也不能把没读过的位置当作读完了。
- **落盘顺序**：读出的数据先写进镜像，坏区图里这一段才记为已读。最多每 5 秒、每轮开始和结束（含停止、出错）时保存一次：先让镜像数据落盘（`sync_data`），再把坏区图写进 `.map.tmp`、落盘、改名替换 `.map`。任何时候盘上都是一份完整的坏区图，而且它记为已读的数据一定已在盘上；崩溃或断电最多重读最近几秒的区域。
- **新建**：镜像文件或坏区图已存在时拒绝（`IMAGE_EXISTS`），界面据此提示续做。输出位置所在的卷支持稀疏文件（NTFS）时，镜像建成稀疏文件（`FSCTL_SET_SPARSE`）再 `set_len`：没读的区域不占空间，往远处写也不用先把前面填 0（普通文件往有效数据长度之后写，文件系统要先补零，从 1 TB 处开始写要补好几个小时）；这时不预留空间，开始前核对剩余空间不小于这一次最多要写的量（范围里还没读完的字节数），不够时答复 `OUTPUT_UNAVAILABLE`。不支持稀疏文件的卷（FAT32、exFAT）按源的容量整块 `set_len`，只能整盘做。读不出的区域保持为 0，输出盘空间不足、FAT32 放不下 4 GiB 以上的文件在开始时就报错（这一次刚建的文件随即删掉，不留空壳）；随后保存一份全部未读、记着当前分区表的坏区图。Windows 上镜像以只允许别人读的共享方式打开，同一个镜像不会被两个任务同时续做。
- **续做**：读回坏区图，容量、扇区大小、来源要与当前的源一致，镜像文件长度要等于容量，否则拒绝（`IMAGE_MISMATCH`；这两项核对是 `image_job::check_header`、`check_length`，`image.inspect` 用同一份）；只读一部分时镜像必须是稀疏文件（旧版本建的、FAT32 / exFAT 上的只能整盘做）。然后清掉 `reset` 的范围，记下源上现在的分区表，从坏区图里还没完成的那一轮接着做，已读出的区段不再读。
- **做之前看一眼**（`image.inspect`，引擎 `image_inspect`）：按浏览时的办法读分区表、识别文件系统（界面用同一套文字描述分区），列出分区与超过 1 MiB 的空隙，各带坏区图里的进展。已有镜像能续做时：坏区图里记了分区表的，按编号与现在的分区表对比，列出多了、不见了、位置或大小变了的分区；抽查从镜像里已读出的部分一共取 32 块（按各段已读出的量分配，每段至少一块，第一块取这一段最前面读出的位置，其余随机），每块最多 64 KiB，与源上同一位置比较，读不出的另计。对不上说明做镜像之后源被写过（例如增删改了文件），界面让用户选重做变化的部分、保留旧内容接着做，或者另建新镜像。
- **做过的镜像**：宿主在每次开始制作时记下镜像位置、当时选的源、来源标识与容量（第 7 章）；`image.describe` 只读坏区图给出现在的状态，镜像被删除、移走时据此提示。
- **连接异常（初版）**：每次读错之后，先重读最近一个读成功的扇区（续做时取坏区图里第一段已读区域的开头）。它也读不出，说明设备本身读不到了（多半是断开），这次错误不记入坏区图，存好坏区图后结束，结果里带上停下的位置；检查连接后续做即可。还没有任何读成功的扇区时无从核对，照常记录。已读的扇区事后真的坏了时也会按断开处理，续做时换一个已读扇区核对。
- **输出位置**：源为物理磁盘时，在创建任何文件或目录之前核对镜像不在这块盘上，规则与深度恢复的输出目录相同（第 5.4 节）；镜像文件做源时，镜像与坏区图都不能是来源文件本身。
- 镜像文件不记录扇区大小，宿主打开镜像时一律按 512 字节；4Kn 盘做出的镜像要按坏区图里的扇区大小打开，在后续加入。

### 5.7 文件系统检查与修复（exFAT、FAT）

依据微软公开的 exFAT 与 FAT 文件系统规范实现。

| 阶段 | 只读检查的内容 |
|---|---|
| 引导区 | 主引导区与备份引导区是否一致；exFAT 引导校验和扇区；几何参数是否自洽（规则与打开卷、引导扇区诊断相同，第 5.10 节；形式上不合规范但不影响使用的记为可以忽略） |
| 分配表 | FAT 链：越界、循环、交叉链接、提前结束 |
| 分配位图（exFAT） | 位图与实际占用逐簇比对 |
| 目录树 | 目录项集合的校验和、条目类型与次序、文件名哈希、长度与簇数是否相符；大写表 |
| 汇总 | 丢失簇（已占用但没有文件引用）、大小不符、坏簇标记 |

- **结果**：问题清单，按"会丢数据 / 结构错误 / 可以忽略"分级。每项列出位置、影响和可选修法，例如"截断到可读长度""另存为孤立文件""在 FAT 中标记为坏簇"。
- **修复**：用户勾选后，`repair.planFsFix` 生成写入计划（第 4.2 节），改前备份、改后读回校验、可回滚。默认先在镜像上修，确认结果后再决定是否写回原盘。
- **坏扇区**：检查只读元数据，不做整盘扫描，正常的盘几秒到几分钟就能查完。整盘坏区扫描由用户单独发起，与镜像共用读取策略。
- **进度**：阶段列表，加上本阶段的进度、已处理条目数、已发现的问题数；随时可以取消。
- **NTFS**：没有公开规范，只提供引导扇区与 MFT 镜像相关的检查和修复，不做全面修复。

**第一阶段（已实现，只读）**：`yisi-repair` 的 `check` 模块，引擎方法 `fs.check`。只检查、列出问题，不生成写入计划（`repair.planFsFix` 与写盘在后续阶段）。实现了的检查：

| 项目（`checked` / `skipped` 里的名字） | FAT12/16/32 | exFAT | NTFS |
|---|---|---|---|
| 引导扇区参数（`boot`） | BPB 各项、卷是否超出分区、FAT 能否装下全部簇；FAT32 的 FSInfo 签名 | 各项参数、应为 0 的保留区、卷是否超出分区、VolumeFlags 的未正常卸下与介质故障位 | 扇区与簇大小、MFT 记录大小、卷是否超出分区 |
| 备份引导扇区（`backupBoot`） | FAT32：位置与认法同打开卷、引导扇区诊断（第 5.10 节），找不到可用的备份记 `backupBootInvalid`；按诊断的字段表逐字段比对主备，一个不同的字段记一条 `backupBootMismatch`（`field`，主的值在 `expected`、备份的在 `actual`） | 同左；另核对备份引导区的校验和 | 同左 |
| 引导区校验和（`bootChecksum`） | — | 主、备引导区的校验和扇区 | — |
| 两份 FAT（`fatCopies`） | 逐表项比对（FAT32 关闭镜像时不比） | — | — |
| FAT 链（`chains`） | 起始簇不合法、越界或保留值、成环、指向空闲簇、经过坏簇、链长与文件大小不符；第 0 项（低 8 位是介质描述符、其余位全为 1，与丢失分区搜索的判断相同）、第 1 项的脏标记与硬错误标记，坏簇计数 | 同左；「不走 FAT 链」的文件按连续存放核对范围 | — |
| 目录项（`entries`） | 长文件名的校验和与序号、残留的长文件名项、子目录的 `.` 与 `..` | 目录项集合的校验和、次项个数、文件名长度与文件名项个数、有效数据长度不大于文件长度、不属于任何文件的流扩展项与文件名项 | — |
| 交叉链接（`crossLinks`）、丢失簇（`lostClusters`） | 认领表：每个簇记下第一个认领它的文件，再被认领就是交叉链接；FAT 里已占用却没人认领的是丢失簇（逐段列出前 100 段，其余合成一项） | 同左，「已占用」以分配位图为准 | — |
| 分配位图（`bitmap`） | — | 有人认领的簇在位图里必须已分配（按文件汇总） | — |
| 大写表（`upcase`） | — | 存在，表的校验和 | — |
| `$MFT`（`mft`）、`$MFTMirr`（`mftMirror`） | — | — | 位置在卷内；`$MFT` 第一条记录可用（签名、更新序列、记录头都对，在用，是基本记录；与打开卷的判断相同）；`$MFTMirr` 与 `$MFT` 前 4 条记录逐字节一致 |

- **问题**：每项有类型（`kind`，如 `chainLoop`、`crossLink`、`lostClusters`、`entrySetChecksum`、`bootChecksum`、`unreadable`）、严重程度（`dataLoss` 会丢数据 / `structure` 结构错误 / `minor` 可以忽略，由类型决定）、涉及的路径或簇、读不出的位置，以及引导扇区里出问题的那一项（`field`）。说明与以后的修法由界面按类型给出（`fsCheck.issue.*`），引擎不出用户可见的句子。
- **主引导扇区不能用时**（判断与打开卷相同）按打开卷、引导扇区诊断同一套候选位置与认法找备份（第 5.10 节），找到就记一项 `bootUnrecognized`、按备份接着查；主引导扇区还认得出是哪种文件系统时，另按 `bpb` 列出它哪几项不对。都不能用时报 `unknownFilesystem`。
- **读不出的扇区**：整段读不出时逐扇区重读，读不出的补 0、记成 `unreadable`（标明在读哪个结构或目录），同一位置只记一次；落在读不出区段里的 FAT 表项与目录项不作判断，检查照常往下走。
- **规模**：FAT 按 64 KiB 分块缓存（最多 32 MiB）；认领表每簇 4 字节，超过 6400 万个簇（256 MiB）时不建，交叉链接、丢失簇与分配位图记为没能检查。一个目录最多读 256 MiB、最多嵌套 256 层。
- **没做的**：exFAT 文件名哈希（Windows 不核对）；FAT32 FSInfo 的空闲簇数（只是提示，Windows 正常卸下的卷也常对不上，对照镜像里实测差 759 簇）；TexFAT 的第二份 FAT；NTFS 的目录与位图。

### 5.8 文件找回（FAT、exFAT、NTFS）

FAT、exFAT 依据微软公开的规范实现；NTFS 没有官方规范，依据公开的结构资料实现，不参考其他实现的代码。只读源盘。ext2/3/4 在之后加入。

**分区表（`yisi-part`）**

- 第 0 扇区有 GPT 保护项（类型 0xEE）时读 GPT：表头签名、表头 CRC-32、表头记录的自身位置、表项 CRC-32 都要对；主表坏了读设备末尾的备份表（位置取主表头里记的，主表头坏了取最后一个扇区）。设备报告 512 字节扇区而表是按 4096 字节写的（USB 硬盘盒换过的盘），再按 4096 试一次。
- 否则读 MBR：只认状态字节为 0x00 或 0x80 的表项；扩展分区沿 EBR 链列出逻辑分区（编号从 5 起），链读不出、没有签名、成环或超过 128 个时停在断点。
- 第 0 扇区以跳转指令开头、带 exFAT / NTFS 标识或 BPB 参数自洽时，当作整块设备就是一个文件系统（U 盘不分区直接格式化）。识别不出任何分区表时同样按整块设备处理。
- 超出设备末尾的分区截短，起点在末尾之外的不列出；这些情况和「改用了备份 GPT」都作为说明随分区表返回。
- 用途按 MBR 类型字节、GPT 类型 GUID 识别常见的几种（EFI 系统、Microsoft 保留、基本数据、Windows 恢复、Linux 等）；文件系统另按分区开头的引导扇区识别：FAT12/16/32、exFAT、NTFS、BitLocker、ext2/3/4。

**目录读取（`yisi-fs`）**

- FAT 的类型按簇数判定（规范第 3.5 节），只是 BPB 里 16 位的 FAT 扇区数为 0 时按 FAT32 处理。分区被截短时簇区只算到分区末尾。FAT32 不镜像时只读指定的那一份 FAT。
- 卷标取根目录里的卷标项，没有才用引导扇区里的（Windows 改卷标只改根目录）。
- 表项、首簇、长文件名、exFAT 目录项集合的规则在 `yisi-fs` 的 `format` 模块，文件系统检查用同一份。FAT12/16 目录项的第 20、21 字节不是首簇的高位，只有 FAT32 才拼上。
- 长文件名：各段校验和要等于短文件名的校验和，未删除的还要序号从 `0x40 | n` 递减到 1、不超过 20 段，否则只用短文件名。短文件名按大小写标记显示，非 ASCII 字节（OEM 代码页）显示为 `_`。
- exFAT 按目录项集合解析：次项个数 2–18，第一个次项是流扩展项、文件名项紧跟其后且个数与名字长度相符，使用中标记要一致，集合校验和要对（删除的集合按删除前的类型字节计算），否则跳过。
- FAT 表和 exFAT 分配位图按 64 KiB 分块缓存（最多 32 MiB）；目录最多读 64 MiB、列 100 万项，簇链长度超过簇总数即视为成环。

**删除文件的识别与可信度**

| | FAT12/16/32 | exFAT | NTFS |
|---|---|---|---|
| 怎么认 | 目录项首字节为 0xE5 | 目录项类型的「使用中」位为 0 | MFT 记录头的「在用」位为 0（扫一遍 MFT 找出） |
| 名字 | 首字母丢了：有长文件名时按校验和反推（校验和对首字节一一对应），没有时首字母显示为 `_`，标「名字不完整」 | 完整 | 完整（Win32 名；另有 DOS 名时作短文件名） |
| 内容在哪 | 簇链已清零，只能假设从首簇起连续存放 | 「不走 FAT 链」的文件本来就连续；其余的 FAT 表项删除后一般还在，沿链读，链断了才按连续假设 | 运行表删除后还在，碎片文件也按原位置读；小文件的内容常驻在记录里 |
| 可能完整 | 按连续假设占用的簇在 FAT 里都空闲 | 占用的簇在分配位图里都空闲，且位置可信 | 运行表里的簇在 `$Bitmap` 里都空闲，或内容常驻在记录里 |
| 已被覆盖 | 有簇已分给别的文件 | 有簇在分配位图里已被占用 | 有簇在 `$Bitmap` 里已被占用 |
| 无法判断 | 首簇不在合法范围；FAT32 簇数超过 16 位、首簇高 16 位为 0 时，按低位找到的簇已被占用，说不准是真被覆盖还是首簇的高位被早年的 Windows 清掉了 | 首簇不在合法范围；链断了改按连续假设 | 运行表越界或接不上；属性列表指向的扩展记录对不上；删除时被截成 0 字节（见下） |

- 已删除的目录：FAT 只读首簇起连续、空闲的簇，直到遇到目录结束标记；首簇开头必须还是 `.` 与 `..`，否则判为已被覆盖、列不出内容。已删除目录里的项一律按已删除处理。
- 已知看不出的情况：FAT 里删除前就有碎片的文件，按连续假设读出的内容不对，但只要中间的簇空闲，仍判为「可能完整」；父目录已被覆盖的文件沿目录树找不到。界面写明「可能完整」只看占用情况，复制出来要打开核对，找不到的去用深度恢复。

**NTFS（`yisi-fs` 的 `ntfs` 模块）**

- 引导扇区：除了 `NTFS` 标识，扇区大小、簇大小（含 64 KiB 以上的写法）、MFT 记录大小、`$MFT` 的位置也要自洽，才认作 NTFS（规则见第 5.10 节的逐项核对）。`$MFT` 的第 0 条记录读不出时用 `$MFTMirr` 里的副本。
- MFT 记录：签名 `FILE`、更新序列修正（每 512 字节末尾两个字节写盘时换成了更新序列号，对不上说明没写完整，整条不用），Windows XP 起记录头里的记录号也要对。常驻与非常驻属性都能读，非常驻的按运行表读，稀疏的部分读作 0，有效数据长度之后读作 0。
- 属性列表（`$ATTRIBUTE_LIST`）：跟到扩展记录，扩展记录的基本记录引用要指回来、序号要对（已删除的文件扩展记录一同释放，序号可能已加 1），各段运行表按虚拟簇号接起来。`$MFT` 自己碎片多时也有属性列表，先用基本记录里的第一段运行表读出扩展记录。
- 列目录：读 `$I30` 索引，`INDEX_ROOT` 里的项，加上 `INDEX_ALLOCATION` 里按 `$BITMAP` 标为在用的索引块里的项（索引块同样做更新序列修正；只为列出，不按 B+ 树次序走）。名字取 Win32 / POSIX 命名空间，同一记录的 DOS 名作短文件名；0–15 号系统文件、目录自己不列出。长度、时间、属性取索引项（NTFS 会同步更新索引里的这份副本；记录里的 `$FILE_NAME` 长度常年不更新，实测碎片文件为 0）。扫过 MFT 后，长度、数据位置与存放方式以记录为准，记录已删除或序号对不上的旧索引项不列出。一个目录的索引最多读 256 MiB、100 万项。
- 扫描 MFT：先读 `$Bitmap`（不超过 512 MiB 时整份读进内存，读不出的部分按已占用算），再按 1 MiB 一段顺序读 MFT，整段读不出时逐条重读、只放弃读不出的记录。每条记录留 24 字节摘要（序号、在用、目录、长度、数据位置、存放方式、可信度），已删除的另留名字与父目录引用；MFT 超过 1600 万条记录时不扫。实测（只读）：C 盘（NVMe）75 万条记录、745 MiB，0.93 秒；F 盘（USB 机械盘）209 万条、2.0 GiB，21 秒。
- 挂回目录树：父目录还在用时，子项记的父目录序号必须相等；父目录也已删除时接受相等或差 1（删除时记录的序号加 1，子项记的是删除前的，VHD 实测）。父记录已被别的文件重用、不是目录、或就是自己的，列进根目录下的虚拟目录「找不到原目录的文件」。实测 C 盘 35 万个已删除项里有 33.5 万个在这里，多是 Windows 更新展开到临时文件夹又删掉的组件清单，临时文件夹的记录早已被别的文件重用。
- 删除时被截断：Windows 删除碎片多到要用属性列表的文件时，先把它截成 0 字节：数据流变空、扩展记录清空、属性列表改写，记录里 `$FILE_NAME` 的长度也是 0。这类文件的位置和长度都已不在 MFT 里，判为「无法判断」，读取时说明原因（VHD 实测）。
- 暂不支持读出的存放方式：NTFS 压缩、EFS 加密、系统压缩（WOF，重分析标记 0x80000017，C 盘上很多系统文件是这种）、符号链接与目录联接、没有本地内容的其他重分析点（云端占位文件）。列表里加文字标签，不预览、不打开，复制时记为失败并写明原因。备用数据流不列出，只读无名数据流。
- 时间：NTFS 记的是 UTC，FAT / exFAT 记的是写入时的本地时间；都按 `yyyy-MM-dd HH:mm:ss` 显示，NTFS 的标注 UTC。
- 定位信息：NTFS 为 `n1-d…-x…-m<记录号>-q<序号>-s<长度>`，虚拟目录为 `n1-o`。读取时核对记录的序号、在用状态与定位信息一致，记录被重用后，旧的定位信息读不了。
- 已知看不出的情况：固态硬盘开了 TRIM 时，删除的文件的簇常常已被清零，判为「可能完整」读出来却全是 0（复制时检出整份为 0 的文件并提示）；簇被重新分配又释放过的文件，判为「可能完整」但内容不对。

**浏览会话（引擎）**

- `repair.open` 起一个长驻的浏览任务：读出分区表、识别各分区的文件系统、打开能浏览的分区取卷标，答复后一直运行到取消或宿主断开。
- `repair.listFiles` 与 `repair.previewFile` 在后台线程里答复，不挡住取消请求。目录第一次被列出时整份读出，按「目录在前、名字不分大小写、同名时未删除的在前」排好序缓存（最多 64 个目录），之后按页给出：一页最多 1000 项，编码后超过 768 KiB 就提前结束这一页，保证一条消息不超过 1 MiB。
- 每一项带一个定位信息（FAT / exFAT 是首簇、长度、有效数据长度、是否目录、是否删除、是否连续；NTFS 是 MFT 记录号与序号），界面原样传回；引擎解码后照样做越界检查，伪造的定位信息最多读到同一个卷里的其他簇或其他记录。
- NTFS 分区列出已删除的项之前要先 `repair.scanDeleted`：扫描在后台线程里进行，期间浏览任务发 `job.progress`（`stage` 为 `scanMft`）；`repair.cancelScan` 或关闭浏览时停下，下次重扫。同一分区同一时间只扫一遍，扫完清掉这个分区已缓存的目录。
- 打开会话时可以指定用备份引导扇区（`boot: backup`，第 5.10 节）：整个会话里各分区都按备份识别和打开，没有有效备份的分区（FAT12/16、备份也坏了）认作「未识别」、不能浏览。复制任务带同样的 `boot`。

**复制（`repair.copyFiles`）**

- 单独起一个任务引擎，浏览照常进行。参数里带浏览时的分区编号、偏移和长度，引擎重新读分区表核对，对不上就拒绝。
- 输出规则与深度恢复相同：源为物理磁盘时先核对输出目录不在源盘上（`OUTPUT_ON_SOURCE`，第 5.4 节），之后在输出目录下新建 `restored-<任务 ID 前 8 位>` 子目录。
- 选中的目录连同全部内容一起复制（最多 64 层、100 万项），先展开再复制，进度按总字节数算。保留相对路径；每一级名字清洗成各系统都能用的形式（去掉控制字符和 `<>:"/\|?*`、去掉结尾的点和空格、避开 `CON`、`NUL`、`COM1` 这类保留名、截到 255 个 UTF-16 单元），同一目录下重名（例如同名的已删除文件与现存文件）时加序号，不覆盖已有文件。
- 每个文件先写 `名字.part`，写完改名，目标已存在时不覆盖（与深度恢复同一个函数，`yisi_carve::rename_new`）；名字与本任务起过的、目录里已有的文件或别人还在写的 `.part` 重名时加序号；以 `.part` 结尾的名字把那个点换成 `_`（这个后缀留给写入中途的文件，宿主不打开）。读源出错（簇链断了、读错误、存放方式不支持）记为这个文件失败、继续下一个；写输出出错（例如输出盘满）整个任务失败。复制好的文件经 `job.copied` 分批通知（每批最多 100 个或 250 毫秒；正在复制一个大文件时也按时发出之前攒下的），长度以实际读出的为准，整份为 0 的标 `allZero`。
- NTFS 分区上选了目录时，复制引擎先扫一遍 MFT（与浏览不是同一个进程，扫描结果不共享），目录里已删除的项才能一起复制；扫描的进度带 `stage`。

### 5.9 丢失分区搜索

只读：不写回分区表，也不改动源。找到的分区可以浏览、把文件另存到别的盘；把分区写回分区表要等写入计划（第 4.2 节）。

**找引导扇区（`yisi-repair` 的 `search` 模块）**

- 从头到尾按 1 MiB 一段顺序读源（与读取扫描同一个函数 `yisi_io::scan_device`），每 512 字节看一次：以跳转指令（`EB` / `E9`）开头、以 `55 AA` 结尾的扇区交给 `yisi-fs` 的 `boot` 模块里的 `inspect_boot` 判断是不是 FAT12/16/32、exFAT、NTFS 的引导扇区，参数是否自洽沿用各文件系统打开时的规则（第 5.8 节）；exFAT 另要求卷长度装得下簇区。读不出的一段整段跳过、计入读不出的字节数。4 KiB 扇区的盘上分区同样落在 512 字节的边界上。
- 每个引导扇区按两种假设推算分区起点：它就在分区开头（主引导扇区）；它是备份（FAT32 是 BPB 第 50 字节记的扇区，一般是第 6 扇区，必须在保留区里；exFAT 是第 12 扇区起的备份引导区；NTFS 是卷的最后一个扇区，引导扇区里的扇区数不含它）。卷长度：FAT 是总扇区数，exFAT 是卷长度字段，NTFS 是扇区数加 1。
- 单是引导扇区自洽不够，引导扇区的副本随处都有（备份、镜像文件里的、格式化前留下的），每个假设再核对一处结构：FAT 的任一份 FAT 第 0 项是介质描述符、其余位全为 1；exFAT 这次用的引导区（主或备份）的校验和对，并且 FAT 第 0 项是 `F8 FF FF FF`；NTFS 的 `$MFT` 或 `$MFTMirr` 第一条记录是可用的 `$MFT` 自身记录（与打开卷、文件系统检查的判断相同）。把备份当主引导扇区的假设，起点错开几个扇区，FAT 与 `$MFT` 的位置随之错开，核对不过。
- 起点、卷长度、文件系统都相同的合并成一个候选分区：主引导扇区与备份都对得上为「both」，只有备份对得上为「backup」（这时记下备份的位置），否则「primary」。最多 1000 个候选，超出时说明。超出源末尾的卷截短并标出。
- 卷标：打开卷取（FAT 优先根目录里的卷标项），只靠备份找到的用备份引导扇区打开。
- 与现有分区表比对：起点相同为「表里已有」（给出编号）；否则与哪个分区有重叠就是「重叠」，都没有为「丢失」。整块设备（无分区表）与 GPT 保护项覆盖整块盘，不拿来判断重叠。候选分区之间有重叠时都标出，其中至少一个不是真的（例如分区里存着的磁盘镜像文件），由用户浏览里面的文件分辨。
- 进度按读过的字节数；每读一段查一次取消、过一次暂停闸门。

**浏览与复制**

- 浏览会话（第 5.8 节）用 `repair.openRange` 按位置打开候选分区，之后列目录、预览、扫描 MFT 与表里的分区走同一套代码。只靠备份找到的分区带 `boot: backup`，按备份引导扇区打开（`Volume::open_with`，找备份的规则与引导扇区诊断相同，第 5.10 节），主引导扇区读不出也能打开。
- 复制同样单独起一个任务引擎（第 5.8 节），参数带按位置打开时的分区编号与 `boot`，引擎按编号认出它不在表里，不核对分区表。

**已知看不出的情况**：只认 FAT12/16/32、exFAT、NTFS；结构核对只看开头的几个字节，主 FAT 与备份 FAT 都坏了的 FAT 分区、`$MFT` 与 `$MFTMirr` 开头都坏了的 NTFS 分区找不到；被取消的搜索不保留已经找到的分区。

### 5.10 引导扇区诊断

「修复打不开的分区」的第一阶段：只读，先诊断，主引导扇区坏了、备份完好时用备份浏览并另存文件。不写回引导扇区（写回要走写入计划，后续版本先在镜像上做）。FAT、exFAT 依据微软公开的规范，NTFS 依据公开的结构资料。

**备份在哪（`yisi-fs` 的 `boot` 模块）**

| 文件系统 | 备份位置 | 主引导扇区坏了时怎么找 |
|---|---|---|
| FAT32 | 引导扇区第 50 字节记的扇区（通常是 6；0 与 0xFFFF 表示没有，不在保留区里的不算，另记一条不影响使用的提醒） | 按第 6 扇区找 |
| exFAT | 第 12–23 扇区是备份引导区（引导扇区、8 个扩展引导扇区、OEM 参数、保留、校验和扇区） | 第 12 扇区 |
| NTFS | 卷的最后一个扇区之后、也就是分区的最后一个扇区（卷长度比分区少一个扇区） | 先按主引导扇区记的卷长度找，再找分区最后一个扇区 |
| FAT12/16 | 没有备份 | — |

- 主引导扇区坏了，扇区大小也就不可信：按主引导扇区里还认得出的值、设备的逻辑扇区大小、512、4096、1024、2048 依次试。读出的扇区参数自洽，并且它记的扇区大小与它所在的位置相符，才算找到。
- 主引导扇区里残留的标识（exFAT、NTFS 的 OEM 标识，FAT32 的类型字符串）决定先试哪种文件系统；全清零时三种都试。
- `Volume::open_with(…, BootCopy::Backup)` 用找到的备份打开卷，之后的列目录、读文件与用主引导扇区时完全一样；`detect_with` 同理。诊断与浏览用同一套找法，诊断说「备份可用」的分区，浏览时一定找得到同一份备份。

**逐项核对（`yisi-fs` 的 `bpb`）**

规则只有一份：打开卷、丢失分区搜索、引导扇区诊断（`yisi-repair` 的 `boot`）与文件系统检查（第 5.7 节）都按它核对，所以诊断说「核对通过」的引导扇区一定打得开，检查与浏览对同一份引导扇区也不会有两种说法。每一项问题标明是否致命：致命的让参数不可用，卷打不开、诊断算这一份坏了、检查到此为止；不致命的（下表中带 * 的）只报告，卷照常打开，诊断列为「提醒」。前一项不合法时，依赖它的后几项不再核对，免得一个错报成一串。一致性由测试钉住：样本的主引导扇区随机改坏数百次，三处的结论每次都相同；备份引导扇区随机改坏，诊断与检查对「备份能不能用」「哪些字段与主引导扇区不同」每次都相同。

| | FAT12/16/32 | exFAT | NTFS |
|---|---|---|---|
| 标志 | 结尾 `55 AA`；开头跳转指令* | 同左；跳转指令 `EB 76 90`*；OEM 标识 `EXFAT`；第 11–63 字节为 0 | 同左；OEM 标识 `NTFS`；保留扇区数、FAT 个数等旧字段为 0* |
| 扇区与簇 | 每扇区 512–4096 字节；每簇扇区数为 2 的幂、不超过 128 | 扇区 2^9–2^12 字节；簇不超过 32 MiB | 扇区 512–4096 字节；簇不超过 2 MiB（含 64 KiB 以上的写法） |
| 区域 | 保留扇区数不为 0；FAT 1 或 2 份、大小不为 0、装得下全部簇*；FAT12/16 的根目录项数不为 0、FAT32 的为 0；数据区在卷内，簇数在这种 FAT 的范围内；FAT32 的根目录簇号在范围内、不镜像时指定的那份 FAT 存在 | FAT 起点不小于 24；FAT 装得下全部簇*；簇区在 FAT 之后、卷装得下簇区*；簇数、根目录簇号在范围内 | MFT 记录大小合法、索引块大小合法*；`$MFT` 的起始簇在卷内、`$MFTMirr` 的在卷内* |
| 其他 | 介质描述符 | 引导区校验和（前 11 个扇区，跳过卷标志与使用百分比，与第 12 扇区里重复的值比对） | — |

- 整个扇区是同一个字节时只报「被清零了」，读不出时只报「读不出」，不再逐项列。
- 备份另核对它记的扇区大小与找到它的位置是否相符。
- 主备都认得出是同一种文件系统时，逐个字段比较，列出不一样的。比哪些字段只有一份（`bpb::significant_fields`），文件系统检查按同一份比，字段用规范里的名字（界面按 `bootField.*` 显示）：FAT 比每扇区字节数、每簇扇区数、保留扇区数、FAT 份数、根目录项数、总扇区数、介质描述符、FAT 大小、隐藏扇区数、卷序列号，FAT32 另比镜像标志、根目录簇、FSInfo 与备份引导扇区的位置；exFAT 比分区起点、卷长度、FAT 与簇区的位置和长度、簇数、根目录簇、卷序列号、扇区与簇大小、FAT 份数（卷标志与使用百分比只在主引导扇区里更新，不比）；NTFS 比扇区与簇大小、隐藏扇区数、总扇区数、`$MFT` 与 `$MFTMirr` 的位置、记录与索引块大小、卷序列号（64 位，拆成低、高 32 位两项：值经 JSON 数字传给界面，超过 2^53 会丢精度；Windows 显示的是低 32 位）。引导代码等其余字节不比。
- 引导扇区核对通过的那一份，再按它真的打开卷：打不开说明问题在文件系统内部（例如 MFT 坏了），写明原因，不算引导扇区的问题。

**分区表与引导扇区**

- 类型：MBR 的类型字节要是这种文件系统用的（FAT12/16 为 0x01、0x04、0x06、0x0E，FAT32 为 0x0B、0x0C，NTFS / exFAT 为 0x07，各自的隐藏写法加 0x10，EFI 系统分区 0xEF、恢复分区 0x27、动态磁盘 0x42 也接受）；GPT 只在类型明显不是 Windows 文件系统时（Microsoft 保留、Linux、APFS、HFS+ 等）算不符。
- 长度：引导扇区记的卷（NTFS 再加上卷后的备份扇区）比分区长，说明分区表的长度可能被改小了，超出的部分读不到；分区比卷长出 1 MiB 以上，说明分区表的长度可能被改大了。用来比对的是核对通过的那一份（主的优先）。

**结论**

| 结论 | 条件 |
|---|---|
| 正常 | 主引导扇区核对通过；有备份的，备份也通过 |
| 备份有问题 | 主引导扇区通过，备份不通过 |
| 主引导扇区坏了，备份可用 | 主引导扇区不通过，备份通过；备份能打开卷时界面给出「用备份浏览」 |
| 主备都坏了 | 都不通过，或没有备份（FAT12/16） |
| 不诊断 | BitLocker、ext |
| 认不出 | 主引导扇区、各处备份都认不出，分区类型也推不出（只按 FAT 的几种类型字节与 EFI 系统分区推测；0x07 分不出 NTFS 还是 exFAT） |

分区表本身的问题另列，不改变上面的结论。已知看不出的情况：分区表的长度被改小、NTFS 的备份落到分区之外时，分区最后一个扇区不是备份，报「备份有问题」，同时报卷比分区长。

## 6. 界面

### 6.1 按问题导航与场景向导

首页按用户遇到的问题组织，而不是按技术菜单。窗口左侧是导航栏：

- **首页**（默认显示）：「你遇到了什么问题？」概览，四张问题卡片（名称加一句症状）、一条通用提醒（找回之前不要往出问题的盘上写东西）和到「全部功能」的入口。默认停在概览而不是第一个问题：用户最需要的是先对照症状挑出自己的情况，四个问题并排看最容易比较。
- **问题页**（四项）：每页依次是「什么情况选这里」（症状）、「按这个顺序试」（功能卡片，带步骤序号和针对这个问题的一句说明）、「注意事项」。各问题推荐的功能与顺序：

  | 问题 | 推荐顺序 |
  |---|---|
  | 误删了文件 | 找回删除的文件 → 按文件类型深度恢复 |
  | 分区打不开 / 提示要格式化 | 按文件类型深度恢复 → 修复打不开的分区 → 检查文件系统 |
  | 分区或盘符不见了 | 找回丢失的分区 → 按文件类型深度恢复 |
  | 磁盘有坏道 / 读写很慢或报错 | 坏道检测 → 制作磁盘镜像 → 在镜像上找回删除的文件或按文件类型深度恢复 |

- **全部功能**：七个功能平铺成卡片，能用的在前，给已经知道要用什么的用户直达。卡片按窗口宽度自动排两到四列（每列至少 340px）。
- **关于**：程序版本、恢复引擎是否可用（每次打开现查 `engine.capabilities`）；引擎版本与支持的操作折叠在「技术细节」里。

功能卡片写明功能做什么、适合的情况与局限（做不到的事、使用前提、用不上的情形，标签是「局限」而不是「不适合」，免得前提条件被读成「不适合」的情形）。还没做的功能卡片变淡、虚线边框，带「开发中」文字标签，不只靠颜色区分；仍然可以用 Tab 聚焦，标 `aria-disabled="true"`，读屏软件先读到原因，点击不进入。问题、功能与推荐顺序集中在 `navigation.ts`，文案在 `problems.*`、`features.*` 下（症状与注意事项是字符串数组，条数随语言可以不同）。

导航页与功能页在同一页面里用条件渲染切换，不用路由。焦点：在导航栏切换时留在导航项上；从首页点问题卡片时落在问题页标题；进入功能页时落在功能页标题；从功能页「返回」时回到进入前的导航页，落在刚才点的那张卡片上。进入功能页时导航栏收起：功能运行中不能离开（「返回」按钮此时不可用），导航栏留着会绕过这个限制。

每个向导的步骤是：选择磁盘或镜像 → 分析 → 确认结果 → 执行 → 报告。任务读源时，进度条下方按 `job.reading` 的统计说明读得慢的原因（`useReadHealth` 判断，`ReadHealthHint` 显示，只在源是物理磁盘时）：读错过、或者不止一次单次读取超过 2 秒，或者一次读取卡了 10 秒以上，算碰上了损坏，建议先停下、制作镜像，再在镜像上继续（坏道检测里换一种说法：读到坏区在意料之中）；没有这些迹象时，只在最近 10 秒的读速低于 20 MiB/s、而且读取占了这段时间一半以上（否则慢在计算，与盘无关）时才提示：平均每次读不到 256 KiB 的是内容零散（小文件、碎片多），说明这是正常的、做镜像也快不了多少；每次读得不少的是盘本身慢，说明只做一次不必先做镜像、要反复扫时先做镜像。暂停时不看读速。

已接入的功能页是「找回删除的文件」「按文件类型深度恢复」「坏道检测」「制作磁盘镜像」「修复打不开的分区」「找回丢失的分区」与「检查文件系统」。它们共用来源选择（`SourcePicker`，状态与选出的源在 `useSourceSelection`：镜像文件、整块物理磁盘或其中一个卷；「找回删除的文件」另有「文件夹」，读它所在的卷，扫描后在目录树里逐级展开到这个文件夹（`FsBrowser` 的 `revealPath`，找不到某一级时停在上一级并说明），默认只看已删除的文件）和框架样式（`styles/wizard.css`），向导还共用预览展示（`FilePreviewView`）；浏览分区并另存文件的那一步（`PartitionFiles`：目录树 `FsBrowser`、详情 `FsEntryDetails`、另存为的进度与结果）由「找回删除的文件」「修复打不开的分区」与「找回丢失的分区」共用，浏览会话由使用方打开和关闭；选择分区的表格（`PartitionPicker`）由「找回删除的文件」与「检查文件系统」共用；文件系统名、分区用途、来源等显示文字集中在 `usePartitionText`。

其余共用件：步骤条 `WizardSteps`（全部向导）；任务进行中的暂停 / 继续与取消按钮 `JobControls`（各任务页）；扫描 MFT 的进度 `MftScanProgress`（找回删除的文件、找回丢失的分区）；读不出的区段表 `UnreadableRanges`（坏道检测、制作镜像）；读得慢的原因 `ReadHealthHint`（各任务页）；底栏的引擎状态 `EngineStatus`（各任务的 `useJob` 把自己的状态报给 `useEngineStatus`，底栏显示其中最要紧的一个：运行中、启动中、正在停止、无响应时圆点闪烁，分别为绿、蓝、黄、红；空闲灰、浏览会话开着等待操作绿、暂停黄、引擎不可用红，都不闪；颜色之外总有文字，系统设了减少动态效果时不闪；没有任务时显示程序启动时查到的引擎在不在）；没能保存或复制的文件清单 `FailureList`；选文件夹对话框与它的出错提示 `useHostDialog`；两个树列表（`FsBrowser`、`RecoveredBrowser`）的行窗口、当前行与上下翻页键 `useTreeNavigation`；用时、十六进制、字节数的格式在 `utils/format`。

样式：`wizard.css` 除向导版式外，还有单页工具（坏道检测、制作镜像）的 `tool__*`、树列表的 `tree-list__*`、详情卡片的 `detail-card__*`，以及 `wizard__files`（列表与详情两栏的网格）、`wizard__list`、`wizard__failures`、`wizard__choices` / `wizard__choice`；导航页的卡片 `nav-card` 在 `guide.css`。框体最小高度（`--box-min-height`，与树列表的 10 行一致）、控件圆角（`--radius-control`）、状态颜色（`--color-success` 等）在 `base.css` 的设计变量里；只给读屏软件读的文字用 `wizard.css` 的 `wizard__visually-hidden`。外框固定铺满窗口，`body` 不滚动，只在内容区 `.app-main` 里滚动；`.app-main` 是相对定位，里面绝对定位的元素以它为参照，不会把整页撑高（曾经因此整页能滚、标题栏被推出去、底下露出空白）。

文案：跨页面的通用词句在 `common`（上一步、下一步、取消、暂停、继续、引擎无响应、正在启动、用时、来源、保存在、大小与位置的写法、读不出的区段表头等）；分区文件这块共用界面（目录树、详情、复制、扫描 MFT、文件状态）的文案在 `partitionFiles`；分区相关的共用文案（文件系统名、用途、分区一行描述、选择分区的表格、分区表说明、来源）在 `partition`。各功能自己的命名空间只放本功能独有的文案，不借用别的功能的键。

导航页不限宽度，跟着窗口铺满。两个向导的版式一致：上一步、下一步（开始扫描、暂停与继续、重新扫描、取消）放在顶部步骤条的右边；结果区左边是文件列表、右边是详情，两栏各分标题、框体、底部提示三行（CSS subgrid），三行的上下边对齐。结果页铺满窗口剩下的高度（`.wizard--fill`：内容区、向导、表单到文件区一路 `flex: 1`），列表框与详情框分到多出来的高度，至少 10 行；窗口太矮时整页滚动。列表框和详情框都不按内容撑高（`contain: size`），内容超出时在框里滚动；虚拟列表用 `ResizeObserver` 量出框能显示几行，据此渲染与翻页。保存都用「另存为…」，每次弹出系统的选择文件夹对话框，页面上不常驻保存路径。

**坏道检测**（`BadSectorCheck`）是读取扫描（`disk.readScan`）的界面：把整块盘或镜像从头到尾顺序读一遍（每次 1 MiB，读不出就跳过、不重试），报告读取字节、读不出的区段数与字节数、用时；有读不出的区段时列出前 20 段的起始位置与长度，引擎最多记 1000 段，超出时说明总字节数仍包括全部。页面上先写明结果怎么看（没有读不出的区段、有读不出的区段、读速偏低、只读一次的局限），结果下方按有没有读不出的区段给出下一步：有坏道且数据重要时先做镜像，再在镜像上恢复。

深度恢复向导分三步，扫描本身什么都不写，用「扫描」而不是「恢复」称呼它，免得让人以为会写盘：

1. **来源**：镜像文件（路径框，或系统的选择文件对话框）或物理磁盘（与坏道检测共用磁盘列表 `DiskPicker`：分「本地磁盘」「外接磁盘」两组，USB、SD、MMC 或可移动的算外接；每块盘一张卡片，只放名称、容量、分区表格式、固态或机械、盘符与文件系统，接口、扇区大小、序列号、各卷已用多少收在「详情」里）。
2. **格式**：列表来自 `carve.listFileTypes`，默认勾选各格式的默认设置；格式名按扩展名取本地化文案。这一步的主按钮就是「开始扫描」，不再另设一步确认。下方折叠着可选的「扫描时直接保存」：勾选并给出目录（系统的选择文件夹对话框，路径框也可以直接编辑）后边扫边保存，源为物理磁盘时提示输出必须在另一块盘上，开始时由引擎再核对一次（第 5.4 节）。整盘都要找回、文件又多时用它，省去另存时再读一遍源。
3. **扫描**：进度与读速，可以取消；结束后一行报告（找到的文件数与大小、读不出的区域、用时，边扫边保存时加上保存位置），按格式的数量与大小看列表的分组。运行中不能返回上一步或离开，步骤条右边是「暂停 / 继续」与「取消」，结束后是「重新扫描」。暂停时状态行写明停在哪里、暂停期间不读盘，已找到的文件照常可以查看、预览。找到的文件边扫边列在下方：
   - 左边是两级树，可以按格式或按磁盘位置分组。按位置分组时，每段的大小取 2 的幂，至少 1 MiB，段数不超过 32。单击分组展开或收起，单击文件在右边看详情与预览，双击文件打开；键盘上下移动、左右收起展开、回车打开。行高固定，只渲染看得见的行，十万级文件也不卡；
   - 右键文件（或在列表里按菜单键、Shift+F10）弹出菜单：打开、打开方式…（系统的「打开方式」对话框）、复制（把文件放到剪贴板，可以到文件夹里粘贴）、另存为…（系统的另存为对话框，可以改名）、在文件夹中显示。菜单可以用方向键、Home/End 移动，回车执行，Esc、Tab 或点到别处关闭，关闭后焦点回到列表；靠近窗口边缘时往回挪；
   - 右边是详情（文件名、格式、大小，起始与结束位置：结束位置是最后一个字节，各给出字节偏移与扇区号）、预览（第 6.3 节），以及「打开」「另存为…」「在文件夹中显示」；
   - 扫描中、完成后、取消后都能查看。选中文件 150 毫秒后才请引擎读取，方向键快速移动时不为途经的每个文件起一个引擎；晚到的旧答复丢弃。
   - 只扫描时：每行有勾选框（空格也能勾选，勾选分组即选中整组），预览直接从源上读；扫描结束（完成或取消）后，列表下方是「另存为…（N 个）」：选一个文件夹，勾选的文件存进去（第 5.4 节），下面显示保存进度、没能保存的文件与原因、已另存数。还有没另存的结果时，离开、返回或重新扫描前先确认。
   - 还没另存的文件，打开、打开方式、复制之前先在程序目录下的 `open-cache` 里存一份副本（只显示一行「正在准备文件…」），存好再做；下一次为打开、复制存副本时，宿主在后台清掉以前的副本。副本不算已另存，不能「在文件夹中显示」。程序目录存不进去（在被扫描的盘上，或没有写权限）时，改为请用户选一个保存位置，按另存处理。扫描或保存进行中，这几项与另存为不可用。

找回删除的文件向导分三步：

1. **来源**：同深度恢复。点「下一步」时打开浏览会话、读出分区表，物理磁盘这时请求提权。
2. **分区**：表格列出编号、卷标、文件系统、用途、起始位置、大小，读分区表时的说明列在上方；不能浏览的分区置灰并写明原因（BitLocker 已加密、认不出、NTFS 的 `$MFT` 读不出等）。NTFS 分区点「下一步」先扫描 MFT：进度条与已读、总字节数，可以取消（留在这一步，下次重扫），失败时写明原因；扫过的分区再进入不重扫。回到来源这一步时关闭会话。
3. **浏览与复制**：
   - 左边是分区的目录树：单击文件夹展开或收起，第一次展开时才向引擎要内容，按页加载，「还有 N 项」的行滚进视野就加载下一页；行高固定、只渲染看得见的行。已删除的项名字划线、变淡，并带「已删除 · 可能完整 / 已被覆盖 / 无法判断」的文字标签，不只靠颜色区分；可以只看已删除的文件（目录都保留）。每行一个勾选框，空格勾选；上级目录已勾选时，里面的项显示为已勾选（淡一些、点了不变，提示要先取消文件夹），复制时不再单列；
   - 存放方式不支持的项（NTFS 压缩、加密、系统压缩、链接）另带「… · 暂不支持」的文字标签，详情里写明原因，不预览、不打开；「找不到原目录的文件」是斜体的虚拟目录；
   - NTFS 分区上方写明扫描结果（记录数、已删除数、找不到原目录的数、读不出的记录数），下方提示时间是 UTC；
   - 右边是详情（名字、短文件名、路径、状态说明、存放方式、大小、修改与创建时间，NTFS 标注 UTC、数据位置、MFT 记录号）与预览；
   - 双击文件或点「用默认程序打开」：先在程序目录下的 `open-cache` 里复制一份（只显示一行「正在准备文件…」），复制好再交给系统打开；程序目录存不进去时改为请用户选保存位置。可执行与脚本类文件不打开，改为在文件夹中显示；
   - 「只看已删除的文件」在列表标题行；列表下方是「另存为…（N 项）」：选一个文件夹，在里面新建 `restored-` 开头的子目录复制进去。下面是进度（NTFS 先扫描 MFT 时显示扫描进度）、失败清单与内容全为 0 的文件清单（各最多列 20 个）、汇总与「在文件夹中显示」。复制进行中不能返回或离开。
   - 源是物理磁盘时提示：分区正在使用时读到的可能不是最新状态，找回删除的文件前先停止往这块盘写东西。

找回丢失的分区向导（`FindPartitionsWizard`）分三步，页面上写明这一版只读、不写回分区表，先把文件另存到别的盘：

1. **来源**：同深度恢复，主按钮是「开始搜索」。
2. **搜索**：进度与读速；步骤条右边是「暂停 / 继续」与「取消」，运行中不能返回或离开。暂停时状态行写明停在哪里、暂停期间不读盘。取消或失败后是「重新搜索」。完成后自动进入结果，有找到分区时打开浏览会话（物理磁盘这时可能再请求一次提权）。
3. **结果**：上方一行摘要（找到几个、现有分区表、用时、读不出的字节数、超出上限时的说明）。下面三栏，与找回删除的文件一样各分标题、框体、底部三行（subgrid）对齐：左边是找到的分区（单选列表：文件系统、大小、卷标、起始位置，以及「丢失 / 分区表里已有（分区 N）/ 与分区 N 重叠」「主引导扇区已坏，按备份找到」「与另一个找到的分区重叠」「超出磁盘末尾」这些文字标签，不只靠颜色区分），中间与右边是 `PartitionFiles`。选中一个分区时按位置打开它，NTFS 先扫描 MFT（进度与取消在右边的框里，扫过的不再扫），停下或失败时写明原因并给「重新打开」；打开、扫描、复制进行中不能换分区、返回或离开。步骤条右边是「上一步」（回到来源，关闭浏览）与「重新搜索」。

**修复打不开的分区**（`RepairPartitionWizard`）是引导扇区诊断（第 5.10 节）的界面，分三步：

1. **来源**：同深度恢复，上方一句说明读哪些位置。主按钮是「开始诊断」。
2. **诊断**：只在读取中（物理磁盘这时请求提权）或失败时停留，失败时写明原因、可以重试；读完直接进入结果。
3. **结果**：上方是源与分区表的概况，以及固定的一句「这一阶段只诊断、不写盘：不会把备份写回引导扇区；备份可用时先用备份把文件另存到别的盘；真正的修复要等后续版本，届时会先在镜像上做」。每个分区一节：
   - 标题是编号、卷标（能打开的那一份读出的）、文件系统、大小；下面是结论（结论的文字加语义色，不只靠颜色）与一句解释；
   - 分区类型（MBR 附类型字节）与起点；主引导扇区与备份引导扇区各自的位置（扇区号与字节偏移）、记的卷大小与簇大小、问题清单或「各项核对都正常」，不影响使用的问题另列为「提醒」；FAT12/16 写明没有备份；
   - 主备不一样的字段列成表；分区表与引导扇区不符时另列（类型不符写明两边各是什么）；引导扇区正常却打不开卷时写明原因；最后按结论给出下一步建议；
   - 主引导扇区坏了、备份能打开卷时有「用备份浏览并另存文件」：按备份打开浏览会话，结果页换成与「找回删除的文件」第 3 步相同的浏览与另存（铺满窗口），上方提示正在按备份浏览、不会写回；步骤条右边的按钮变成「返回诊断结果」，返回时关闭会话。另存进行中不能返回或离开。
   - 步骤条右边是「上一步」（回到来源）与「重新诊断」。

**制作磁盘镜像**（`DiskImage`）是 `image.create` / `image.resume` 的界面：页面上先写明怎么做的（三轮读取、坏区图、分几次做与先只复制完好区域、空间要求），另有一段可展开的「什么情况下能接着做」（镜像与 `.map` 要在一起、同一个源、两次之间不写原盘、按分区做要放在 NTFS 盘上、意外关闭最多丢最后几秒的进度）。

- **做过的镜像**（`ImageHistoryList`，`useImageHistory`）：列出宿主记下的镜像，每条是位置、来源、上次保存的时间与现在的状态（做到哪了；找不到了、只剩镜像文件或坏区图、坏区图读不懂时说明原因）。「选用」填上路径和当时的源（物理盘按 `identity` 找现在的编号，原来的盘没接上时提示）；找不到或只剩一个文件时可以「重新指定位置…」（选镜像文件现在的位置，旁边要有同名的 `.map`，来源与容量对得上才改记录）；「从列表移除」只删记录，不删文件。
- 「① 要复制的盘（来源）」默认选物理磁盘；「② 镜像保存到」填镜像文件的完整路径，「选择文件夹…」选好文件夹后自动接上默认文件名（物理盘为 `disk<编号>.img`，镜像文件为 `<原文件名>-image.img`）。源与路径都有了、停下 0.7 秒后调用 `image.inspect`（`useImageInspection`，只认最后一次的答复），源或路径一变，手上的结果作废。
- **这个位置已有镜像**时显示它做到哪了；不能续做（只有一个文件、坏区图读不懂、不是这个源做的、长度不对）时说明原因，不让开始，给出「换个位置新建」。源在上次之后变过（分区表变了、抽查对不上）时逐条列出，让用户选「重做变化的部分」（把变化前后的分区位置与对不上的段放进 `reset`）、「保留旧内容接着做」或「另建新镜像…」，选了才能开始。旧版本做的镜像没记分区表时说明只能靠抽查。
- 「③ 复制哪些部分」：「整盘」，或「只做选中的分区」（`ImageRegionPicker`：分区与空隙可多选，每行给出未开始、已复制几成、已完成、坏区附近待细读，抽查的结果）；镜像不能是稀疏文件时（输出盘不是 NTFS、旧版本建的镜像）只能整盘，说明原因。说明总会一起读的分区表区域多大；已有进度时可以勾选清掉所选部分的进度、从头重读；可以勾选「先只复制完好区域」。给出这一次最多还要写入多少与输出盘的剩余空间，稀疏镜像放不下时不让开始；选中的都已做完又没勾重做时说明没有要读的。按钮在能续做时是「继续制作」。
- 运行中显示当前轮次、本次范围内已读出与范围大小、读不出的字节数、还没读完的三类字节数、读速，复制这一轮另给出预计剩余时间；进度条按「已经有结论的字节数」走（只复制完好区域时读错的块也算过了这一遍）。「停止（之后可以继续）」存好坏区图后结束；停止后、源设备读不到之后都显示「继续制作」，按同一个源、同一路径、同样的范围续做（不再清进度）。结束（完成、停止、失败）后重新查看一次，各段的状态随之更新，可以接着选剩下的。
- 完成后报告本次范围的读出、读不出的区段数与字节数，只做一部分时另给出整盘已读与还没读的量，本次用时、镜像与坏区图的路径，列出前 20 段读不出的位置；只复制了完好区域时说明还有多少留到以后、怎样补读；只做了一部分时说明之后选同一个镜像接着做。最后提示在「找回删除的文件」或「按文件类型深度恢复」里选这个镜像文件；有读不出的位置时说明它们在镜像里是 0。

**检查文件系统**（`FsCheckWizard`）是 `fs.check` 的界面，四步：

1. **来源**：同深度恢复。页面上写明这一版只检查、不修复、不改动磁盘，修复要等后续版本、届时先在镜像上做；盘有坏道时先做镜像，再检查镜像。点「下一步」时打开浏览会话、读出分区表。
2. **分区**：表格同「找回删除的文件」。FAT12/16/32、exFAT、NTFS 可以选，认不出或读不出引导扇区的也可以选（检查会试备份引导扇区），各带一句附注（NTFS 只查引导扇区与 `$MFT` 的位置）；BitLocker、ext 等置灰。主按钮是「开始检查」：先关闭浏览会话，再开始检查。
3. **检查**：进度条与当前阶段（检查引导区、读 FAT 与分配位图、遍历目录树、逐簇汇总），步骤条右边是「暂停 / 继续」与「取消」；暂停时写明暂停期间不读盘。失败或取消后留在这一步，可以「重新检查」。完成后自动进入结果。
4. **结果**（`.wizard--fill`）：来源、分区、文件系统概况（簇大小与簇数、文件与文件夹数）、各严重程度的问题数与用时、检查了与没能检查的项目、读不出的字节数。问题清单按「会丢数据 / 结构错误 / 可以忽略」分组，组名带文字与一句解释，不只靠颜色；每项是可以展开的 `<details>`：标题一句话说清哪里坏了，展开后是说明、涉及的路径与簇、源上的位置、以后可以怎么修。清单框铺满剩下的高度（至少约 10 行），不按内容撑高，在框里滚动。步骤条右边是「导出问题清单…」与「重新检查」：导出用系统的另存为对话框，按当前语言生成 `.txt`（概况、各组问题与修法、只读与先做镜像的说明），宿主命令 `fs_check_save_report` 只接受 `.txt` 的完整路径，检查的是物理磁盘时不许存到这块盘上、检查的是一个卷时不许存到这个卷上（`outputOnSource`；判断与引擎核对输出目录是同样的函数 `yisi_io::ensure_off_source`、`ensure_off_volume`，查不到也拒绝）。「上一步」重新读分区表回到分区这一步。

引导扇区诊断是一次性的查询（宿主另起引擎、答复后退出），不经过任务状态。坏道检测（读取扫描）、深度恢复、浏览会话、复制、制作镜像、丢失分区搜索、文件系统检查共用同一套任务状态（`useJob`：启动、取消、进度、无响应与恢复、终结），各自只处理自己的结果。

**专家模式**展开全部参数和实时日志，保证所有能力都有入口。

### 6.2 可视化

- 分区布局条：按比例显示分区、空闲区和找到的候选分区。
- 扫描扇区图：已扫描、已恢复、坏区分色显示；制作镜像时显示坏区图中各区段的状态。
- 检查结果：问题清单按严重程度分组，每项可以展开看位置、影响和修法。
- 恢复统计：按文件类型统计数量和大小。

### 6.3 预览安全

恢复出的文件**不交给 WebView 直接渲染**。图片由引擎解码后生成缩略图；文本转义后以纯文本显示；其他类型只显示元数据和十六进制视图。恢复出的 HTML、SVG 等文件在 WebView 中会执行脚本。

目前的实现（深度恢复的结果）：

- 宿主每次预览起一个一次性引擎调用 `preview.file`，与列盘、列格式一样，查完即退出；解码只在没有特权的引擎进程里进行。
- 内容是 JPEG 或 PNG（按文件头判断，不看扩展名）时解码，缩到最长边 512 像素（小图不放大），重新编码成 PNG，以 `data:` 地址交给界面显示（CSP 的 `img-src` 已允许 `data:`）。超过 64 MiB 的图片不解码；解码限制边长 16384、内存 256 MiB，残缺或伪造的图片只回「无法显示」和原因。
- 其他格式显示开头 4 KiB 的十六进制与 ASCII。现有格式都不是文本，纯文本预览等有文本格式时再加。
- 「找回删除的文件」里的文件同样由引擎读取、解码（`repair.previewFile`），内容直接从源盘读，规则与上面相同；文件本身不写到任何地方，也不交给 WebView。
- 预览、打开、打开方式、复制、在文件夹中显示都只接受任务 ID 加一级文件名（恢复时起的、另存为时起的或加了序号的；不能含路径分隔符与 `:`，不能以 `.part` 结尾），宿主在该任务的输出目录里找，解析（含联接与符号链接）后必须仍直接在这个目录里，不接受其他路径。分区浏览复制出的文件同样规则，只是接受以 `/` 分隔的多级相对路径（每一级同样不能含 `:`，最后一级不能以 `.part` 结尾），解析后必须仍在输出目录之内；两者是宿主里同一个函数。界面遇到 `executableBlocked` 时改为在文件夹中显示并说明原因，深度恢复与分区浏览同一个做法（`openOrReveal`）。输出目录取自 `carve.start` 或 `carve.extract` 的答复，宿主记到退出为止，任务结束后仍可查看。另存为时可以改名，所以打开与打开方式同样不打开可执行与脚本类文件（`executableBlocked`）。
- 只扫描、还没保存的文件：界面只给扫描任务 ID 加 偏移、长度，宿主回到这个扫描任务的源上（同一个镜像，或请代理重新打开同一块磁盘），另起引擎调用 `preview.range`；读超出源末尾的部分截掉。
- 「用默认程序打开」交给系统，按文件类型由对应程序处理，不经过 WebView。

## 7. 宿主

- 管理引擎进程与代理进程的启动、心跳、退出。引擎程序与宿主程序放在同一目录；Windows 上以 `CREATE_NO_WINDOW` 启动，不弹出控制台窗口。
- 把引擎事件合并后转给界面，界面侧不直接面对高频事件。界面只收一个事件 `job-event`，载荷是 `{jobId, kind, data}`，`kind` 为 progress、found、copied、imaging、reading、log、completed、failed、cancelled、unresponsive、responsive。
- 任务 ID 由界面生成（UUID），在调用启动命令之前就记下，避免事件先于命令返回到达时被丢掉；宿主只接受字母、数字和连字符。
- 返回给界面的错误是 `{code, detail}`：`code` 由界面翻译成当前语言，`detail` 是技术细节。引擎答复的错误码中，`SOURCE_UNAVAILABLE`、`OUTPUT_UNAVAILABLE`、`OUTPUT_ON_SOURCE` 分别转成 `sourceUnavailable`、`outputUnavailable`、`outputOnSource`，其余统一为 `engineRejected`。
- 界面给的源（`Target`）是镜像文件、物理磁盘编号或卷的盘符，宿主按它请代理打开设备（`resolve_source`）。读取扫描用 `job_start_read_scan`（源），与其他任务一样。
- 磁盘代理在整个会话里只启动一次（第一次需要打开物理磁盘时），之后复用；宿主退出时代理随之退出。等待 UAC 期间，其他打开请求排队，不会同时弹出多个 UAC。代理程序同样放在宿主程序旁边，`tauri dev` / `tauri build` 会先编出引擎和代理。
- 本地保存任务记录，界面重启后可以看到历史任务并续传。
- Tauri 安全配置：严格 CSP；禁止加载远程内容；只开放白名单中的命令。系统文件对话框用官方的 dialog 插件，capability 只开放 `dialog:allow-open`（选择文件与文件夹）与 `dialog:allow-save`（另存为）。
- 深度恢复只扫描时：`carve_preview_range`、`job_start_extract` 只接受扫描任务 ID，源取宿主记下的这个任务的源，界面不能借此读别的设备。保存任务的输出目录同样记下，保存好的文件按保存任务 ID 加文件名打开。
- 打开恢复出的文件、在文件夹中显示，用官方 opener 插件提供的 Rust 函数，由宿主自己的命令 `recovered_open`、`recovered_reveal` 调用。插件不注册、不开放给界面，界面无法让宿主打开任意路径。引擎答复的 `PREVIEW_UNAVAILABLE` 转成 `previewUnavailable`。
- 「打开方式」（`recovered_open_with`）启动 `rundll32.exe shell32.dll,OpenAs_RunDLL <路径>`，由系统显示对话框；路径不加引号（加了反而认不出），由前一条的文件名规则保证只是输出目录里的一个文件。「复制」（`recovered_copy`）启动 PowerShell 执行 `Set-Clipboard -LiteralPath`，路径经环境变量传入、不拼进命令文本，失败时答复 `copyFailed`。
- `job_start_extract` 不给输出目录时是为打开、复制存副本，输出目录与后台清理见第 5.4 节。
- 浏览分区：`browse_open` 起浏览任务（与扫描一样，物理盘先请代理复制只读句柄），`browse_list`、`browse_preview` 转给这个任务的引擎，等答复最多 120 秒（十万级目录、慢速 USB 盘）；`browse_scan` 等到扫完（有进度、可以用 `browse_cancel_scan` 停下，上限 24 小时）；关闭浏览用 `job_cancel`；暂停、继续深度恢复用 `job_set_paused`。复制用 `job_start_copy`；不给输出目录时是为打开而复制，与 `job_start_extract` 一样存进 `open-cache`（第 5.4 节）。引擎的 `FS_UNAVAILABLE` 转成 `fsUnavailable`。
- 制作镜像用 `job_start_image`（源、镜像文件的完整路径、是否续做、做法 `plan`：`ranges`、`copyOnly`、`reset`，以及给人看的来源描述），分别转成 `image.create`、`image.resume`；物理盘与其他任务一样先请代理复制只读句柄。引擎的 `IMAGE_EXISTS`、`IMAGE_MISMATCH` 转成 `imageExists`、`imageMismatch`；`job.imaging`、`job.reading` 转成 kind 为 imaging、reading 的事件。`image_inspect` 与引导扇区诊断一样另起引擎查询一次。
- 做过的镜像（`image_history`）：任务开始后把镜像位置、当时选的源、引擎答复的来源标识与容量、来源描述、时间记进程序数据目录的 `image-history.json`（先写临时文件再改名；最多 30 条，最近用的在前，路径在 Windows 上不分大小写）。`image_history_list` 读记录、经 `image.describe` 给出各自现在的状态；`image_history_remove` 只删记录；`image_history_relocate` 要求新位置的状态是 ok、来源标识与容量与记录一致才改（否则 `imageRelocateInvalid`、`imageRelocateMismatch`）。记不下来不影响做镜像，只是下次不能从列表里选。
- 复制出的文件用 `copied_open`、`copied_reveal` 打开或在文件夹中显示：只接受任务 ID 加引擎报告的相对路径，每一级都是普通名字（不含 `:`），最后一级不以 `.part` 结尾，解析（含联接与符号链接）后必须仍在该任务的输出目录之内（与恢复出的文件同一个函数）。找回的文件来路不明，`.exe`、`.bat`、`.cmd`、`.ps1`、`.vbs`、`.js`、`.hta`、`.msi`、`.lnk`、`.url`、`.reg`、`.scr` 等可执行、脚本或会改系统设置的类型不交给系统打开（`executableBlocked`），只能在文件夹中显示。

## 8. 质量目标的设计约束

| 目标 | 约束 |
|---|---|
| **高可用** | 进程隔离，引擎故障不影响界面；深度恢复和镜像都能断点续传；心跳与无响应处理；任务记录持久化；输出盘满自动暂停；连续读错误时暂停并提示检查连接 |
| **鲁棒** | 解析器对任意输入只返回结果或"不认识"，不 panic：禁用 `unwrap`/`expect`/直接下标，来自磁盘的数值一律用带检查的运算；panic 在任务边界捕获并转成任务失败；写入计划带前置哈希、备份、读回校验和回滚；磁盘报错时先镜像后修复，检查与修复分开 |
| **安全** | 解析代码不持有特权；引擎不具备写盘能力；默认只读，写盘必须进入修复模式；不监听端口；恢复文件不进 WebView；每个解析器都有 fuzz 目标；依赖经漏洞与合规检查；安装包签名 |
| **高性能** | 三段流水线；签名查找表；同盘顺序读、多盘并行；事件节流与批量合并；虚拟滚动；性能基准纳入持续集成 |
| **美观** | 统一的设计系统与主题；分区布局、扫描进度、恢复结果可视化 |
| **易用** | 按问题导航与场景向导；专家模式保留全部参数；写入前对比；双语；键盘可达；术语解释 |
