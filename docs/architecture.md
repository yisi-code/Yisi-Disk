# 架构设计

## 1. 目标与范围

### 1.1 功能

| 场景 | 能力 |
|---|---|
| 分区恢复 | 读取并检查分区表；快速搜索与深度搜索丢失的分区；生成并写入新的分区表 |
| 分区修复 | 引导扇区检查、从备份恢复、重建（FAT、NTFS、exFAT、HFS/HFS+、ext 超级块）；FAT 表修复；NTFS MFT 从镜像修复；写入 MBR 引导代码 |
| 文件找回 | 浏览分区目录、复制文件、反删除（FAT、exFAT、NTFS、ext2/3/4） |
| 深度恢复 | 不依赖文件系统，按文件签名在整盘、分区或未分配空间中恢复数百种格式；块大小探测；暴力恢复；断点续传；恢复报告 |
| 文件系统检查与修复 | exFAT、FAT12/16/32 的完整一致性检查：引导区与校验和、FAT 链、分配位图、目录项集合与校验和、大写表，以及交叉链接、丢失簇、越界与循环链。先列出问题清单，用户勾选后生成修复计划；可标记坏簇，孤立的簇链可另存为文件。NTFS 只做有把握的部分（引导扇区、MFT 镜像） |
| 磁盘镜像 | 能识别坏区的镜像：首轮遇错跳过并记入坏区图，先读完完好区域，之后多轮缩小读取粒度回头重试；可暂停、断点续传；坏区图随镜像保存。在镜像上可以执行以上全部操作 |

支持范围：

- **分区表**：MBR（含扩展分区）、GPT、Apple 分区图、Sun、Xbox、Humax、无分区表。
- **文件系统识别**：APFS、BeFS、BSD disklabel、Btrfs、CramFS、exFAT、ext2/3/4、FAT12/16/32、FATX、F2FS、JFS、GFS2、HFS、HFS+、HPFS、LUKS、LVM/LVM2、Linux RAID、NetWare NSS、NTFS、ReFS、ReiserFS、Sun、Linux Swap、System V、UFS/UFS2、VMFS、WBFS、XFS、ZFS。
- **镜像格式**：raw/dd、分段 raw、E01。
- **平台**：Windows 10/11、macOS、Linux 桌面。

### 1.2 质量目标

高可用、鲁棒、安全、高性能、美观、易用。每一项的设计约束见第 8 节。

### 1.3 数据安全原则

- **默认只读。** 所有写盘操作都先生成写入计划，经用户确认后执行（第 4.2 节）。
- **磁盘报读错误时，先镜像，后修复。** 一旦检测到介质错误，界面建议先制作镜像（第 5.6 节）；检查、修复、恢复都在镜像上进行，是否改动原盘由用户最后决定。对出错的盘反复读写会加重损坏。
- **检查与修复分开。** 检查阶段只读，随时可以取消；修复只处理用户勾选的问题，并且改前备份、改后读回校验。

## 2. 总体架构

```
┌──────────────────── 界面进程（普通权限）────────────────────┐
│  Tauri 2 宿主（Rust）  ⇄  界面（Vue 3 + TypeScript）         │
│  任务管理 · 进程守护 · 事件节流 · 本地任务记录               │
└──────────────┬──────────────────────────────┬──────────────┘
               │ JSON-RPC（stdio 管道）        │ JSON-RPC（管道，见 4.1）
┌──────────────▼──────────────────┐  ┌────────▼──────────────────────┐
│ 引擎进程（每个任务一个，普通权限）│  │ 磁盘代理（特权，代码最少）      │
│  engine   任务 / 决策 / 进度 / 取消│◄─┤  打开设备，把只读句柄交给引擎   │
│  repair   分区恢复与修复          │  │  执行写入计划                   │
│  carve    深度恢复                │  │                                 │
│  formats  文件格式插件            │  └───────────────────────────────┘
│  fs       文件系统                │
│  part     分区表                  │
│  io       块设备 / 镜像 / 缓存     │
└─────────────────────────────────┘
```

拆成三类进程的原因：

1. **解析不可信数据的代码不持有特权。** 磁盘内容可能已损坏，也可能被刻意构造。所有解析都在普通权限的引擎进程里进行，即使解析器有缺陷，也拿不到写盘或提权的能力。
2. **故障隔离。** 引擎崩溃、陷入死循环或内存失控，只影响这一个任务；界面会报告原因，可以重试或从断点续传。
3. **特权代码最少、可审查。** 只有磁盘代理持有特权，它只做两件事：打开设备、执行写入计划。列出磁盘只需查询设备属性，由引擎以普通权限完成（第 4.1 节）。
4. **桌面环境限制。** 不少 Linux 桌面（Wayland）默认不允许 root 进程直接开窗口，界面本来就不能以特权身份运行。

宿主与引擎之间走父子进程的 stdio 管道。宿主与磁盘代理之间：Linux 同样走 stdio；Windows 上提权进程接管不了 stdio，改走命名管道（第 4.1 节）。都不监听任何网络端口。

## 3. 进程与通信

### 3.1 协议

- JSON-RPC 2.0，每条消息前加 4 字节小端长度成帧，单条消息不超过 1 MiB。成帧与消息类型在 `yisi-rpc`，宿主、引擎、代理共用。
- 宿主 → 引擎：请求（启动任务、回答决策、取消）。启动任务的请求带上任务 ID（由界面生成），引擎立即答复空对象，之后的进展都以通知送达。
- 引擎 → 宿主：答复，以及不带 id 的通知：`engine.heartbeat`、`job.progress`、`job.log`、`job.completed`、`job.failed`、`job.cancelled`，`job.found`（深度恢复找到的文件）、`job.copied`（复制好的文件）、`job.imaging`（制作镜像的进展：当前轮次、已读与读不出的字节数、各类待读的字节数、最近几秒的读速，每秒最多 5 次），以及之后的 `job.decision`。每条任务通知都带 `jobId`。
- `job.progress` 在引擎侧节流，每秒最多 10 次，完成那一次总会发出；有几个阶段的任务带 `stage`（目前只有 `scanMft`：扫描 MFT，单位是字节）。`found` 事件批量合并后发出。
- 方法名、参数与结果的类型定义在 `yisi-engine` 的库部分（`protocol`），宿主直接引用，不另写一份。

### 3.2 任务生命周期

```
created → running ⇄ waiting_decision → completed
                 ↘ cancelling → cancelled
                 ↘ failed
```

- 每个任务一个引擎进程，任务结束后进程退出。宿主断开（引擎的 stdin 结束）时，引擎取消正在运行的任务后退出。
- 取消：先发 `job.cancel`，引擎在下一个检查点结束任务并发出 `job.cancelled`；5 秒内未退出时，宿主结束进程，仍按取消处理。
- 任务里的 panic 在任务边界捕获，转成 `job.failed`；引擎没有发出终结通知就退出时，宿主按失败处理并带上退出码。
- 心跳：引擎每 2 秒发一次心跳；超过 10 秒没有心跳，标记为无响应，由用户决定等待还是结束；心跳恢复后撤销标记。
- 资源上限：引擎进程设置内存上限（Windows 用作业对象，Linux/macOS 用 rlimit）。

### 3.3 决策事件

恢复流程中需要用户判断的地方（确认写入、选择分区、输入参数等），以决策事件发给界面。引擎阻塞等待答复，流程代码保持顺序写法。

```json
{"type":"decision","jobId":"j1","id":"d7","kind":"confirm","risk":"write",
 "title":"写入分区表","detail":{"before":[...],"after":[...]},
 "options":["apply","cancel"],"default":"cancel"}
```

- `kind`：`confirm`、`select`、`number`、`text`、`location`。
- **`risk` 为 `write` 的决策，默认值固定为取消；等待超时也按取消处理。**

### 3.4 RPC 方法（初版）

| 方法 | 说明 |
|---|---|
| `engine.capabilities` | 返回引擎版本和已支持的功能，界面据此显示或隐藏入口 |
| `disk.list` / `disk.openImage` | 列出物理磁盘（只查询设备属性，普通权限即可）；打开镜像文件 |
| `repair.analyse` | 读取当前分区表并检查结构 |
| `repair.search` | 快速或深度搜索分区（任务） |
| `repair.open` | 浏览分区（任务）：读出分区表、识别各分区的文件系统后答复，之后一直运行到取消，期间接受 `repair.listFiles`、`repair.previewFile`、`repair.scanDeleted`、`repair.cancelScan`（第 5.8 节） |
| `repair.scanDeleted` / `repair.cancelScan` | 找出浏览中的一个分区里已删除的项：NTFS 扫一遍 MFT，期间浏览任务发 `job.progress`（`stage` 为 `scanMft`），扫完答复记录数、已删除数、找不到原目录的数；扫过的分区直接答复上次的结果，其他文件系统立即答复。`repair.cancelScan` 停下正在进行的扫描，那次扫描答复 `cancelled` |
| `repair.listFiles` / `repair.previewFile` | 列出浏览中的一个目录的一页（含已删除的项与可信度）；预览其中一个文件，规则同 `preview.file`。分区或定位信息不对时答复 `FS_UNAVAILABLE` |
| `repair.copyFiles` | 把选中的文件与目录复制到另一块盘（任务），已删除的项同样可以复制（反删除）；NTFS 分区上选了目录时先扫一遍 MFT（进度带 `stage`）。复制好的文件经 `job.copied` 分批通知。源为物理磁盘时规则同 `carve.start` |
| `repair.planPartitionWrite` / `repair.planBootSector` / `repair.planFatRepair` / `repair.planMftRepair` | 只生成写入计划，不写盘 |
| `fs.check` | 文件系统一致性检查（任务，只读）；逐阶段推送进度，边查边推送发现的问题 |
| `repair.planFsFix` | 按用户勾选的问题生成修复用的写入计划 |
| `broker.openDisk` | 磁盘代理以只读方式打开物理磁盘，把句柄复制进指定的引擎进程（第 4.1 节） |
| `broker.executeWrite` | 由磁盘代理执行一份已确认的写入计划 |
| `broker.shutdown` | 结束磁盘代理 |
| `carve.listFileTypes` | 列出全部格式和分组 |
| `carve.start` / `carve.resume` | 启动或续传深度恢复（任务）；接下任务时答复实际输出目录，找到的文件经 `job.found` 分批通知。给了输出目录时边扫边保存，源为物理磁盘时输出目录必须在另一块盘上，否则答复 `OUTPUT_ON_SOURCE`（第 5.4 节）；不给时只扫描、什么都不写，答复的输出目录为空 |
| `carve.extract` | 保存只扫描时选中的文件（任务）：每个文件在源上那一段重新跑一遍深度恢复，起点与长度和扫描时一致才保存；结果经 `job.copied` 分批通知。输出目录规则同 `carve.start` |
| `preview.range` | 预览源上的一段（只扫描、还没保存的文件），规则同 `preview.file` |
| `preview.file` | 预览一个文件：长度、开头 4 KiB；JPEG、PNG 另给缩略图（第 6.3 节）。打不开时答复 `PREVIEW_UNAVAILABLE` |
| `image.create` / `image.resume` | 制作或续做能识别坏区的镜像（任务）：参数是源与镜像文件的完整路径，坏区图是同一路径加 `.map`。建好或打开这两个文件后答复它们的路径，进展经 `job.progress`（`stage` 为轮次）与 `job.imaging` 送达，结果是读出、读不出的字节数与读不出的区段（最多 1000 段）。新建时镜像或坏区图已存在答复 `IMAGE_EXISTS`；续做时坏区图不存在、读不懂，或记录的容量、扇区大小、来源与当前的源不符，答复 `IMAGE_MISMATCH`；源为物理磁盘时规则同 `carve.start`（`OUTPUT_ON_SOURCE`），源为镜像文件时不能写到来源文件自己上。取消时保存坏区图，之后续做（第 5.6 节） |
| `disk.readScan` | 从头到尾顺序读一遍设备或镜像，记下读不出的区段（任务，只读）；整盘坏区扫描的基础 |
| `job.cancel` / `job.status` | 取消任务；查询状态 |

## 4. 特权与设备访问

### 4.1 只读句柄传递

磁盘代理以特权打开设备，把**只读**句柄交给引擎：

| 平台 | 提权方式 | 句柄传递 |
|---|---|---|
| Linux | polkit（pkexec）启动代理 | Unix 套接字 `SCM_RIGHTS` |
| macOS | 系统授权服务 | 与 `authopen` 相同的描述符传递方式 |
| Windows | 代理以管理员身份运行（UAC） | `DuplicateHandle` 复制到引擎进程 |

引擎侧的块设备类型**不提供写方法**，写盘能力在类型层面就不存在于引擎中。

**Windows 的做法。** 普通权限的宿主只能用 `ShellExecuteEx("runas")` 启动提权进程，接管不了它的 stdio，所以宿主与代理之间走命名管道：

- 管道由宿主创建，名字带 128 位随机数；`FILE_FLAG_FIRST_PIPE_INSTANCE` 让抢先占用同名管道的情况直接失败，`PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程连接。
- 管道的 ACL 只允许管理员组和 SYSTEM。提权后的代理属于管理员组；未提权的进程，即使与宿主是同一用户，也连不上。
- 双向核对身份：宿主核对连进来的客户端进程就是刚启动的代理；代理核对管道的服务端进程就是命令行给出的宿主。
- 宿主退出时代理随之退出，管道关闭时代理读到结束后退出，不留下以管理员身份运行的孤儿进程。
- 代理只接受 `\\.\PhysicalDriveN` 形式的路径，不替宿主打开任意文件。
- 代理只读打开设备，用 `DuplicateHandle(…, DUPLICATE_SAME_ACCESS)` 复制进引擎进程，复制出的句柄与原句柄一样只有读权限（实测授予的权限为 `FILE_GENERIC_READ`）。
- 引擎用 `WindowsDisk::adopt_handle` 认领句柄：只接受能回答磁盘 IOCTL 的句柄，同一个值只能认领一次。引擎自己没有权限打开磁盘，这类句柄只能来自代理。

macOS 的特权辅助程序同样没有 stdio，通道在实现 macOS 版时确定（XPC）。

**列出磁盘不需要特权。** Windows 允许普通权限以零访问权限打开 `\\.\PhysicalDriveN`，只查询设备属性、不读写内容：容量与逻辑扇区大小用 `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX`，厂商、型号、序列号、总线与是否可移动用 `IOCTL_STORAGE_QUERY_PROPERTY`。所以 `disk.list` 由引擎完成，用户选好盘、真正要读的时候才需要代理。

**扫描一块物理磁盘的流程（Windows）：**

1. 宿主启动引擎，得到它的进程 ID；
2. 宿主确保代理在运行：第一次需要时提权启动（弹 UAC），之后整个会话复用；代理通信失败时丢掉连接，下次重新启动；
3. 代理只读打开磁盘，把句柄复制进这个引擎；
4. 宿主向引擎发起任务，源为 `{type: "disk", handle}`，引擎用 `WindowsDisk::adopt_handle` 认领后照常读取。

### 4.2 写入计划

所有写盘操作都先由引擎生成写入计划，经用户确认后交给代理执行：

```rust
pub struct WritePlan {
    pub id: PlanId,
    pub device: DeviceIdentity,      // 序列号、容量、扇区大小，防止写错盘
    pub writes: Vec<SectorWrite>,    // 起始扇区、新内容、写前内容的 SHA-256
    pub summary: PlanSummary,        // 给界面展示的修改前后对比
}
```

代理按以下步骤执行，任何一步失败都停止，并报告停在哪一步：

1. 核对设备身份与计划一致；
2. 读取目标扇区，核对写前哈希。不一致说明磁盘在计划生成后被改动过，拒绝执行；
3. 把原扇区内容和元数据写入备份文件；
4. 写入并刷盘；
5. 读回校验；
6. 记录执行结果。

回滚就是把备份文件当成一份新的写入计划执行。

## 5. 引擎模块

### 5.1 模块与依赖方向

```
io ← part ← fs ← repair ─┐
          ↖ formats ← carve ├─ engine
                          ┘
io ← broker
rpc ← engine、broker、宿主（宿主另外引用 engine、broker 的库部分）
```

| 目录 | 包名 | 职责 |
|---|---|---|
| `crates/io` | `yisi-io` | 块设备抽象；Windows/macOS/Linux 后端；raw、分段 raw、E01；读缓存；坏扇区读取策略；能识别坏区的镜像（第 5.6 节） |
| `crates/part` | `yisi-part` | 分区表的解析、校验、序列化与自动识别；CRC-32（GPT 与 PNG 共用） |
| `crates/fs` | `yisi-fs` | 文件系统识别；目录读取（含已删除的项）与文件提取（第 5.8 节）；空闲空间位图；引导扇区与超级块的检查和重建；exFAT / FAT 一致性检查（只读，输出问题清单，第 5.7 节） |
| `crates/formats` | `yisi-formats` | 文件格式插件与注册表 |
| `crates/carve` | `yisi-carve` | 深度恢复：搜索空间、块大小探测、识别分派、数据检查、暴力恢复、断点续传、恢复报告 |
| `crates/repair` | `yisi-repair` | 分区分析与搜索、结构检查、反删除；生成写入计划（分区表、引导扇区、FAT/MFT 修复、文件系统修复） |
| `crates/engine` | `yisi-engine` | 引擎进程入口：任务运行时、决策事件、进度节流、取消。库部分只有宿主与引擎之间的方法与参数（`protocol`），供宿主引用 |
| `crates/broker` | `yisi-broker` | 磁盘代理。库部分供宿主使用：方法与参数、Windows 上建管道和提权启动；程序部分是以管理员身份运行的代理本身 |
| `crates/rpc` | `yisi-rpc` | 成帧与 JSON-RPC 2.0 消息，宿主、引擎、代理共用 |

`formats` 只用 `part` 里的 CRC-32。目前「找回删除的文件」只读，引擎直接调用 `part` 与 `fs`；`repair` 在要生成写入计划时才接入。

**unsafe 边界**：只有 `io` 和 `broker` 允许 `unsafe`，用于平台系统调用，每处都要写清安全性论证；其余模块一律 `#![forbid(unsafe_code)]`。

### 5.2 块设备抽象

```rust
pub trait BlockDevice: Send + Sync {
    fn size(&self) -> u64;
    fn sector_size(&self) -> u32;
    fn read_at(&self, offset: u64, buf: &mut [u8]) -> Result<usize, IoError>;
    fn read_exact_at(&self, offset: u64, buf: &mut [u8]) -> Result<(), IoError>; // 有默认实现
}
```

- `read_at` 的偏移和长度不要求按扇区对齐；读到设备末尾时截断，偏移不小于容量时返回 0。`read_exact_at` 读不满时返回带偏移的错误，供解析器使用。
- 物理盘只接受起点、长度、缓冲区地址都按扇区对齐的读请求。后端在内部处理：请求本身已经对齐时直接读进调用方的缓冲区，否则经对齐的中转缓冲区（每次最多 1 MiB）读取再拷贝。
- Windows 后端以只读、共享读写的方式打开 `\\.\PhysicalDriveN`，不加锁、不独占；容量和逻辑扇区大小用 IOCTL 查询。
- 镜像文件不记录扇区大小，打开时由调用方给出（取来源磁盘的逻辑扇区大小）。扇区大小只接受 512 到 64 KiB 之间的 2 的幂。
- 读错误带上偏移和系统错误码，供坏区策略识别介质错误。
- 读错误按策略处理：重试次数、超时、跳过并记入坏区表，都可以配置。
- 读缓存按扇区对齐；镜像文件优先用内存映射。

### 5.3 文件格式插件

```rust
pub trait FileFormat: Send + Sync {
    fn info(&self) -> &FormatInfo;          // 扩展名、描述、最大尺寸、默认启用
    fn signatures(&self) -> &[Signature];   // (偏移, 魔数)
    fn header_check(&self, block: &[u8]) -> Option<Box<dyn Recovering>>;
}

pub trait Recovering: Send {
    fn data_check(&mut self, offset: u64, block: &[u8]) -> DataCheck; // 继续 / 在某长度处结束 / 无效
    fn open_ended(&self) -> bool;                // 没有结束标志（如 PDF）：遇到下一个文件头时收尾
    fn finish(&mut self, received: u64) -> Option<u64>; // 数据到此为止时的文件长度
    fn waiting_at(&self) -> Option<u64>;         // 正在等待的位置，用来尽早排除长度离谱的误识别
}
```

- **结构遍历器**：大多数格式的插件只实现一个小状态机，每一步告诉遍历器「下一步要从哪里开始的几个字节」（`Need`）、「从哪里开始找什么」（`Scan`）、「文件在这里结束」（`Done`）或「无效」。跨块拼接、跳过大段数据、跨块查找都由遍历器处理，插件不必关心数据怎么分块。遍历器保留最近一次交付或匹配处的字节，插件可以先读签名、再从同一位置读整条记录。
- 一个格式一个源文件，自带样本测试。样本由代码按格式结构现场生成（`yisi-formats` 的 `test-samples` 特性），不放二进制样本进仓库；每个格式还要过同一组随机与变异输入测试，只能给出结果或「不认识」，不能 panic。
- 插件只在能确认文件完整时给出长度，被截短的文件判为不完整、不输出（目前没有「部分恢复」）。没有结束标志的格式要从结构里找证据，例如 MP4（ISO/IEC 14496-12）：
  - 在不认识的顶层 box 处或数据结束处收尾，此前要见过 `moov` 和 `mdat`；
  - 分片文件的 `sidx` 登记了索引内容的长度：sidx 结尾 + `first_offset` + 各条 `referenced_size` 之和（版本 0 为 32 位、版本 1 为 64 位字段），文件至少要到这里，有多个 `sidx` 时取最大值；之后还可以有 `mfra` 等 box；
  - 最后一个 box 不能是 `moof`：它的样本在紧随其后的 `mdat` 里；
  - 看不出的情况：没有 `sidx` 的分片文件正好在一组 `moof` + `mdat` 之后截断；`sidx` 放在单独的索引文件里（以 `styp` 开头，本来就不会被 `ftyp` 签名命中）。
- 注册表在启动时把全部签名建成「偏移 + 前两个字节」的查找表，每个块只查表，不遍历格式。
- 界面上的格式列表来自 `carve.listFileTypes`，不在界面里硬编码。
- 按内容给文件命名（`rename`）在后续加入。

### 5.4 深度恢复流水线

```
读线程 ──(块环形缓冲)──▶ 恢复线程 ──(输出队列，带背压)──▶ 写线程
大块、对齐、顺序读         查签名表、跑格式状态机          写出恢复文件
预读                       维护搜索空间                    检查输出盘空间
```

- 同一块物理盘只有一条顺序读流，避免磁头来回寻道，也减轻对故障盘的压力。
- 读盘、计算、写出三者并行。
- 不同物理盘的任务各开一个引擎进程，可以并行。
- 输出盘空间不足时自动暂停并通知界面。
- 定期写入断点，异常退出后可以续传。

**目前的实现（线性恢复，只处理连续存放的文件）：**

- 按 1 MiB 读设备，再按扇区大小的块处理；文件只可能从块边界开始。整段读不出时逐块重读，只跳过真正读不出的块，正在恢复的文件随之放弃。
- 块开头命中文件头时开始恢复，后续块交给插件判断结尾；结尾之后的下一个块边界继续找。
- 插件判为无效、超过最大尺寸，或到设备末尾仍不完整时，视为误识别，从它的下一块重新找，它覆盖过的块里可能有真正的文件。插件等待的位置已超出设备末尾或最大尺寸时，立即判为误识别。
- 没有结束标志的格式（PDF）遇到下一个文件头时收尾。
- 输出在指定目录下新建 `recovered-<任务 ID 前 8 位>` 子目录；文件名为 `f` 加十位起始扇区号（按 512 字节计），写入期间带 `.part` 后缀，确认完整后才改名。
- **先只扫描、扫完再保存**：`carve.start` 不给输出目录时，写出端换成什么都不写的一个，识别流程完全一样，只记下每个文件在源上的位置、长度和格式，也不需要核对输出盘。保存选中的文件（`carve.extract`）时，把源上每个文件所在的那一段当作一块小设备，只启用它的格式再跑一遍深度恢复：保存时因此重做一遍格式校验，找到的文件起点、长度与扫描时一致才保留，源上的内容在扫描后变了的不保存、报告原因；文件名按在源上的位置起，与边扫边保存时一样。代价是保存时要再读一次源（只读选中的部分）；扫描结果只在内存里，离开前要保存。
- 上面的三段流水线已经实现：读线程顺序读设备，识别在调用线程里进行，写出交给写线程，读盘、识别、写盘同时进行。
  - 读线程按 1 MiB 一段读，最多领先识别 4 段；用完的缓冲区还给读线程重复使用。识别要回头重找（误识别后从它的下一块重找）时，请读线程从新位置重读，队列里旧位置的段丢掉。整段读不出时逐块重读，只标出真正读不出的块（同上）。读线程只会因程序缺陷 panic，这时识别线程把 panic 原样续抛，不会把后面的盘都当成读不出；
  - 0 号盘（NVMe，只读扫描约 1.5 GiB/s）只勾 PDF、1→8.5 GiB 之间没有写出：读与识别在同一线程时 1177–1276 MiB/s（4 次均值 1232），读线程上线后 1159–1403 MiB/s（4 次均值 1314），平均约快 7%，波动与差值同一量级；
  - 识别线程把一个文件的数据攒到 1 MiB 再排进写队列；队列最多 32 条（在途数据约 32 MiB），排满时扫描等待（背压）；
  - 候选文件在第一次交出数据之前就被判为误识别时，输出盘上不建文件；
  - 写线程改好名才回报，「找到的文件」和恢复报告只计入已经改名的文件；取消或扫完时，先把队列里已确认完整的文件写完再结束，100% 进度在写完之后才报；
  - 写线程出错（例如输出盘满）时任务失败，报的是写线程的原始错误。
- 不逐个文件同步到盘：USB 机械盘上每次同步约 100 ms，攒一批再逐个同步也只省一半（每次同步都要让盘刷一次缓存），文件密集处会把扫描拖到每秒十来个文件；整卷一次同步要可写的卷句柄，引擎不具备写盘能力。改了名表示引擎确认文件完整、全部数据已交给操作系统：
  - 引擎崩溃、被结束或任务取消时不受影响，没写完的文件只留 `.part`；
  - 系统崩溃、断电或直接拔掉输出盘时，最近几秒改名的文件可能内容不全。源盘只读，重扫即可找回；拔输出盘前先在系统里安全移除。
- **输出不能写回被扫描的盘**：写出的文件会占用这块盘的空闲空间，而那正是还没找回的数据所在。源为物理磁盘时，引擎在创建任何输出目录之前核对（单是建目录就已经写到了盘上）：
  - 源盘的编号用 `IOCTL_STORAGE_GET_DEVICE_NUMBER` 查询；
  - 输出目录可能还不存在，取最近一级已存在的上级目录打开（随目录联接、符号链接走到真实位置），用 `GetFinalPathNameByHandleW(VOLUME_NAME_GUID)` 得到所在的卷，再用 `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` 查出这个卷落在哪些盘上；还不存在的那几级目录之后才创建，不会改变所在的卷；
  - 卷只要有一段在源盘上就拒绝，答复 `OUTPUT_ON_SOURCE`；任何一项查不到（例如网络路径）同样拒绝，宁可不开始，也不冒险写回源盘；
  - 这些查询都以零访问权限进行，不需要特权，也不读磁盘内容；
  - 查不出的情况：输出在虚拟磁盘（VHD）上、而虚拟磁盘文件本身存放在源盘上时，查到的是虚拟磁盘自己的编号。
- 碎片重组、块大小探测、断点续传在后续阶段加入；恢复报告目前只有按格式统计的数量与大小、读不出的字节数、用时和实际输出目录。

### 5.6 能识别坏区的镜像

```
第 1 轮 复制   大块顺序读；遇错跳过一段（起步 64 KiB，连续出错时加倍，有上限），跳过的区段记入坏区图
第 2 轮 修边   对每个被跳过的区段，从两端按扇区向内读，碰到读错误就停
第 3 轮 细读   对剩下的未读区段逐扇区读一遍
第 4 轮 重试   只对仍然读不出的扇区按设定次数重试
```

- **坏区图**：记录每个区段的状态（未读、已读、待修边、待细读、坏），与镜像放在一起，是纯文本，随时落盘，中断后据此续做。
- **读取策略**：单次读超时、重试次数、跳过大小都可以配置。默认值偏保守，不对出错的盘反复施压；先把能读的读完，最后才碰坏区。
- **连接异常**：短时间内连续出错时暂停并提示检查连接。USB 通道重置也会表现成读错误，换线或换接口后可以续做。
- **输出**：镜像文件加坏区图。读不出的区域在镜像里填零，后续的检查和恢复按坏区图把它们当作"未知"，不当作真实的零。
- **进度**：当前轮次、已读字节、坏区字节、读速、剩余时间；扇区图实时标出各区段状态。

**目前的实现（第 1–3 轮）：**

- 读取策略与坏区图在 `yisi-io` 的 `imaging`，只管读和记；镜像与坏区图怎样落盘由调用方实现（引擎的 `image_job` 写文件，单元测试写内存）。
- **第 1 轮复制**分三遍，读错的块都记为待修边：
  - 正向按 1 MiB 读还没读过的区段；读错后跳过一段，起步 64 KiB，连续出错时加倍，上限是容量的 1/1024（在 64 KiB 到 1 GiB 之间），读成功一次就回到起步值。被跳过的区段仍记为未读；
  - 反向从远端往回读被跳过的区段，同样遇错跳过：碰到坏区时是从完好的一侧靠近它；
  - 最后正向不跳过地补读剩下的未读区段。之后不再有未读的区段。
- **第 2 轮修边**：每个待修边的区段从前往后按扇区读到第一个读错的扇区（记为坏），再从后往前读到第一个读错的扇区（记为坏），中间剩下的记为待细读。读错的那个扇区已经单独读过，细读不再碰它，每个坏扇区只被单独读一次。
- **第 3 轮细读**：待细读的区段逐扇区读一遍，读不出的记为坏。
- 第 4 轮重试、单次读超时、可调的读取参数、暂停（现在「停止」就是存好坏区图后结束，之后续做）和扇区图在后续加入。
- **坏区图格式**（UTF-8 文本，`#` 开头的是注释）：

  ```
  version 1
  size 1000204886016
  sector 512
  source disk WDC WD10EZEX-08WN4A0 WD-WCC6Y0123456
  0 2469203456 done
  2469203456 512 bad
  2469203968 997735682048 untried
  ```

  头部是格式版本、容量、扇区大小与来源标识（物理盘是厂商、型号、序列号，不含会随插拔变化的磁盘编号；镜像文件是规范化后的路径），之后每行一个区段「起始偏移 长度 状态」，状态是 `untried`、`done`、`trim`、`scrape`、`bad`，相邻的同状态区段合并。读回时区段必须首尾相接、覆盖整个设备、状态都认识，否则不续做：坏区图决定哪些位置不再读，宁可不续做，也不能把没读过的位置当作读完了。
- **落盘顺序**：读出的数据先写进镜像，坏区图里这一段才记为已读。最多每 5 秒、每轮开始和结束（含停止、出错）时保存一次：先让镜像数据落盘（`sync_data`），再把坏区图写进 `.map.tmp`、落盘、改名替换 `.map`。任何时候盘上都是一份完整的坏区图，而且它记为已读的数据一定已在盘上；崩溃或断电最多重读最近几秒的区域。
- **新建**：镜像文件或坏区图已存在时拒绝（`IMAGE_EXISTS`），界面据此提示续做。镜像文件一开始就按源的容量 `set_len`：读不出的区域保持为 0，输出盘空间不足、FAT32 放不下 4 GiB 以上的文件在开始时就报错（这一次刚建的文件随即删掉，不留空壳）；随后保存一份全部未读的坏区图。Windows 上镜像以只允许别人读的共享方式打开，同一个镜像不会被两个任务同时续做。
- **续做**：读回坏区图，容量、扇区大小、来源要与当前的源一致，镜像文件长度要等于容量，否则拒绝（`IMAGE_MISMATCH`）；然后从坏区图里还没完成的那一轮接着做，已读出的区段不再读。
- **连接异常（初版）**：每次读错之后，先重读最近一个读成功的扇区（续做时取坏区图里第一段已读区域的开头）。它也读不出，说明设备本身读不到了（多半是断开），这次错误不记入坏区图，存好坏区图后结束，结果里带上停下的位置；检查连接后续做即可。还没有任何读成功的扇区时无从核对，照常记录。已读的扇区事后真的坏了时也会按断开处理，续做时换一个已读扇区核对。
- **输出位置**：源为物理磁盘时，在创建任何文件或目录之前核对镜像不在这块盘上，规则与深度恢复的输出目录相同（第 5.4 节）；镜像文件做源时，镜像与坏区图都不能是来源文件本身。
- 镜像文件不记录扇区大小，宿主打开镜像时一律按 512 字节；4Kn 盘做出的镜像要按坏区图里的扇区大小打开，在后续加入。

### 5.7 文件系统检查与修复（exFAT、FAT）

依据微软公开的 exFAT 与 FAT 文件系统规范实现。

| 阶段 | 只读检查的内容 |
|---|---|
| 引导区 | 主引导区与备份引导区是否一致；exFAT 引导校验和扇区；几何参数是否自洽 |
| 分配表 | FAT 链：越界、循环、交叉链接、提前结束 |
| 分配位图（exFAT） | 位图与实际占用逐簇比对 |
| 目录树 | 目录项集合的校验和、条目类型与次序、文件名哈希、长度与簇数是否相符；大写表 |
| 汇总 | 丢失簇（已占用但没有文件引用）、大小不符、坏簇标记 |

- **结果**：问题清单，按"会丢数据 / 结构错误 / 可以忽略"分级。每项列出位置、影响和可选修法，例如"截断到可读长度""另存为孤立文件""在 FAT 中标记为坏簇"。
- **修复**：用户勾选后，`repair.planFsFix` 生成写入计划（第 4.2 节），改前备份、改后读回校验、可回滚。默认先在镜像上修，确认结果后再决定是否写回原盘。
- **坏扇区**：检查只读元数据，不做整盘扫描，正常的盘几秒到几分钟就能查完。整盘坏区扫描由用户单独发起，与镜像共用读取策略。
- **进度**：阶段列表，加上本阶段的进度、已处理条目数、已发现的问题数；随时可以取消。
- **NTFS**：没有公开规范，只提供引导扇区与 MFT 镜像相关的检查和修复，不做全面修复。

### 5.8 文件找回（FAT、exFAT、NTFS）

FAT、exFAT 依据微软公开的规范实现；NTFS 没有官方规范，依据公开的结构资料实现，不参考其他实现的代码。只读源盘。ext2/3/4 在之后加入。

**分区表（`yisi-part`）**

- 第 0 扇区有 GPT 保护项（类型 0xEE）时读 GPT：表头签名、表头 CRC-32、表头记录的自身位置、表项 CRC-32 都要对；主表坏了读设备末尾的备份表（位置取主表头里记的，主表头坏了取最后一个扇区）。设备报告 512 字节扇区而表是按 4096 字节写的（USB 硬盘盒换过的盘），再按 4096 试一次。
- 否则读 MBR：只认状态字节为 0x00 或 0x80 的表项；扩展分区沿 EBR 链列出逻辑分区（编号从 5 起），链读不出、没有签名、成环或超过 128 个时停在断点。
- 第 0 扇区以跳转指令开头、带 exFAT / NTFS 标识或 BPB 参数自洽时，当作整块设备就是一个文件系统（U 盘不分区直接格式化）。识别不出任何分区表时同样按整块设备处理。
- 超出设备末尾的分区截短，起点在末尾之外的不列出；这些情况和「改用了备份 GPT」都作为说明随分区表返回。
- 用途按 MBR 类型字节、GPT 类型 GUID 识别常见的几种（EFI 系统、Microsoft 保留、基本数据、Windows 恢复、Linux 等）；文件系统另按分区开头的引导扇区识别：FAT12/16/32、exFAT、NTFS、BitLocker、ext2/3/4。

**目录读取（`yisi-fs`）**

- FAT 的类型按簇数判定（规范第 3.5 节），只是 BPB 里 16 位的 FAT 扇区数为 0 时按 FAT32 处理。分区被截短时簇区只算到分区末尾。FAT32 不镜像时只读指定的那一份 FAT。
- 卷标取根目录里的卷标项，没有才用引导扇区里的（Windows 改卷标只改根目录）。
- 长文件名：各段校验和要等于短文件名的校验和，未删除的还要序号从 `0x40 | n` 递减到 1，否则只用短文件名。短文件名按大小写标记显示，非 ASCII 字节（OEM 代码页）显示为 `_`。
- exFAT 按目录项集合解析：类型次序、使用中标记要一致，集合校验和要对（删除的集合按删除前的类型字节计算），否则跳过。
- FAT 表和 exFAT 分配位图按 64 KiB 分块缓存（最多 32 MiB）；目录最多读 64 MiB、列 100 万项，簇链长度超过簇总数即视为成环。

**删除文件的识别与可信度**

| | FAT12/16/32 | exFAT | NTFS |
|---|---|---|---|
| 怎么认 | 目录项首字节为 0xE5 | 目录项类型的「使用中」位为 0 | MFT 记录头的「在用」位为 0（扫一遍 MFT 找出） |
| 名字 | 首字母丢了：有长文件名时按校验和反推（校验和对首字节一一对应），没有时首字母显示为 `_`，标「名字不完整」 | 完整 | 完整（Win32 名；另有 DOS 名时作短文件名） |
| 内容在哪 | 簇链已清零，只能假设从首簇起连续存放 | 「不走 FAT 链」的文件本来就连续；其余的 FAT 表项删除后一般还在，沿链读，链断了才按连续假设 | 运行表删除后还在，碎片文件也按原位置读；小文件的内容常驻在记录里 |
| 可能完整 | 按连续假设占用的簇在 FAT 里都空闲 | 占用的簇在分配位图里都空闲，且位置可信 | 运行表里的簇在 `$Bitmap` 里都空闲，或内容常驻在记录里 |
| 已被覆盖 | 有簇已分给别的文件 | 有簇在分配位图里已被占用 | 有簇在 `$Bitmap` 里已被占用 |
| 无法判断 | 首簇不在合法范围；FAT32 簇数超过 16 位、首簇高 16 位为 0 时，按低位找到的簇已被占用，说不准是真被覆盖还是首簇的高位被早年的 Windows 清掉了 | 首簇不在合法范围；链断了改按连续假设 | 运行表越界或接不上；属性列表指向的扩展记录对不上；删除时被截成 0 字节（见下） |

- 已删除的目录：FAT 只读首簇起连续、空闲的簇，直到遇到目录结束标记；首簇开头必须还是 `.` 与 `..`，否则判为已被覆盖、列不出内容。已删除目录里的项一律按已删除处理。
- 已知看不出的情况：FAT 里删除前就有碎片的文件，按连续假设读出的内容不对，但只要中间的簇空闲，仍判为「可能完整」；父目录已被覆盖的文件沿目录树找不到。界面写明「可能完整」只看占用情况，复制出来要打开核对，找不到的去用深度恢复。

**NTFS（`yisi-fs` 的 `ntfs` 模块）**

- 引导扇区：除了 `NTFS` 标识，扇区大小、簇大小（含 64 KiB 以上的写法）、MFT 记录大小也要自洽，才认作 NTFS。`$MFT` 的第 0 条记录读不出时用 `$MFTMirr` 里的副本。
- MFT 记录：签名 `FILE`、更新序列修正（每 512 字节末尾两个字节写盘时换成了更新序列号，对不上说明没写完整，整条不用），Windows XP 起记录头里的记录号也要对。常驻与非常驻属性都能读，非常驻的按运行表读，稀疏的部分读作 0，有效数据长度之后读作 0。
- 属性列表（`$ATTRIBUTE_LIST`）：跟到扩展记录，扩展记录的基本记录引用要指回来、序号要对（已删除的文件扩展记录一同释放，序号可能已加 1），各段运行表按虚拟簇号接起来。`$MFT` 自己碎片多时也有属性列表，先用基本记录里的第一段运行表读出扩展记录。
- 列目录：读 `$I30` 索引，`INDEX_ROOT` 里的项，加上 `INDEX_ALLOCATION` 里按 `$BITMAP` 标为在用的索引块里的项（索引块同样做更新序列修正；只为列出，不按 B+ 树次序走）。名字取 Win32 / POSIX 命名空间，同一记录的 DOS 名作短文件名；0–15 号系统文件、目录自己不列出。长度、时间、属性取索引项（NTFS 会同步更新索引里的这份副本；记录里的 `$FILE_NAME` 长度常年不更新，实测碎片文件为 0）。扫过 MFT 后，长度、数据位置与存放方式以记录为准，记录已删除或序号对不上的旧索引项不列出。一个目录的索引最多读 256 MiB、100 万项。
- 扫描 MFT：先读 `$Bitmap`（不超过 512 MiB 时整份读进内存，读不出的部分按已占用算），再按 1 MiB 一段顺序读 MFT，整段读不出时逐条重读、只放弃读不出的记录。每条记录留 24 字节摘要（序号、在用、目录、长度、数据位置、存放方式、可信度），已删除的另留名字与父目录引用；MFT 超过 1600 万条记录时不扫。实测（只读）：C 盘（NVMe）75 万条记录、745 MiB，0.93 秒；F 盘（USB 机械盘）209 万条、2.0 GiB，21 秒。
- 挂回目录树：父目录还在用时，子项记的父目录序号必须相等；父目录也已删除时接受相等或差 1（删除时记录的序号加 1，子项记的是删除前的，VHD 实测）。父记录已被别的文件重用、不是目录、或就是自己的，列进根目录下的虚拟目录「找不到原目录的文件」。实测 C 盘 35 万个已删除项里有 33.5 万个在这里，多是 Windows 更新展开到临时文件夹又删掉的组件清单，临时文件夹的记录早已被别的文件重用。
- 删除时被截断：Windows 删除碎片多到要用属性列表的文件时，先把它截成 0 字节：数据流变空、扩展记录清空、属性列表改写，记录里 `$FILE_NAME` 的长度也是 0。这类文件的位置和长度都已不在 MFT 里，判为「无法判断」，读取时说明原因（VHD 实测）。
- 暂不支持读出的存放方式：NTFS 压缩、EFS 加密、系统压缩（WOF，重分析标记 0x80000017，C 盘上很多系统文件是这种）、符号链接与目录联接、没有本地内容的其他重分析点（云端占位文件）。列表里加文字标签，不预览、不打开，复制时记为失败并写明原因。备用数据流不列出，只读无名数据流。
- 时间：NTFS 记的是 UTC，FAT / exFAT 记的是写入时的本地时间；都按 `yyyy-MM-dd HH:mm:ss` 显示，NTFS 的标注 UTC。
- 定位信息：NTFS 为 `n1-d…-x…-m<记录号>-q<序号>-s<长度>`，虚拟目录为 `n1-o`。读取时核对记录的序号、在用状态与定位信息一致，记录被重用后，旧的定位信息读不了。
- 已知看不出的情况：固态硬盘开了 TRIM 时，删除的文件的簇常常已被清零，判为「可能完整」读出来却全是 0（复制时检出整份为 0 的文件并提示）；簇被重新分配又释放过的文件，判为「可能完整」但内容不对。

**浏览会话（引擎）**

- `repair.open` 起一个长驻的浏览任务：读出分区表、识别各分区的文件系统、打开能浏览的分区取卷标，答复后一直运行到取消或宿主断开。
- `repair.listFiles` 与 `repair.previewFile` 在后台线程里答复，不挡住取消请求。目录第一次被列出时整份读出，按「目录在前、名字不分大小写、同名时未删除的在前」排好序缓存（最多 64 个目录），之后按页给出：一页最多 1000 项，编码后超过 768 KiB 就提前结束这一页，保证一条消息不超过 1 MiB。
- 每一项带一个定位信息（FAT / exFAT 是首簇、长度、有效数据长度、是否目录、是否删除、是否连续；NTFS 是 MFT 记录号与序号），界面原样传回；引擎解码后照样做越界检查，伪造的定位信息最多读到同一个卷里的其他簇或其他记录。
- NTFS 分区列出已删除的项之前要先 `repair.scanDeleted`：扫描在后台线程里进行，期间浏览任务发 `job.progress`（`stage` 为 `scanMft`）；`repair.cancelScan` 或关闭浏览时停下，下次重扫。同一分区同一时间只扫一遍，扫完清掉这个分区已缓存的目录。

**复制（`repair.copyFiles`）**

- 单独起一个任务引擎，浏览照常进行。参数里带浏览时的分区编号、偏移和长度，引擎重新读分区表核对，对不上就拒绝。
- 输出规则与深度恢复相同：源为物理磁盘时先核对输出目录不在源盘上（`OUTPUT_ON_SOURCE`，第 5.4 节），之后在输出目录下新建 `restored-<任务 ID 前 8 位>` 子目录。
- 选中的目录连同全部内容一起复制（最多 64 层、100 万项），先展开再复制，进度按总字节数算。保留相对路径；每一级名字清洗成各系统都能用的形式（去掉控制字符和 `<>:"/\|?*`、去掉结尾的点和空格、避开 `CON`、`NUL`、`COM1` 这类保留名、截到 255 个 UTF-16 单元），同一目录下重名（例如同名的已删除文件与现存文件）时加序号，不覆盖已有文件。
- 每个文件先写 `.part`，写完改名；读源出错（簇链断了、读错误、存放方式不支持）记为这个文件失败、继续下一个；写输出出错（例如输出盘满）整个任务失败。复制好的文件经 `job.copied` 分批通知（每批最多 100 个或 250 毫秒），长度以实际读出的为准，整份为 0 的标 `allZero`。
- NTFS 分区上选了目录时，复制引擎先扫一遍 MFT（与浏览不是同一个进程，扫描结果不共享），目录里已删除的项才能一起复制；扫描的进度带 `stage`。

## 6. 界面

### 6.1 按问题导航与场景向导

首页按用户遇到的问题组织，而不是按技术菜单。窗口左侧是导航栏：

- **首页**（默认显示）：「你遇到了什么问题？」概览，四张问题卡片（名称加一句症状）、一条通用提醒（找回之前不要往出问题的盘上写东西）和到「全部功能」的入口。默认停在概览而不是第一个问题：用户最需要的是先对照症状挑出自己的情况，四个问题并排看最容易比较。
- **问题页**（四项）：每页依次是「什么情况选这里」（症状）、「按这个顺序试」（功能卡片，带步骤序号和针对这个问题的一句说明）、「注意事项」。各问题推荐的功能与顺序：

  | 问题 | 推荐顺序 |
  |---|---|
  | 误删了文件 | 找回删除的文件 → 按文件类型深度恢复 |
  | 分区打不开 / 提示要格式化 | 按文件类型深度恢复 → 修复打不开的分区 → 检查并修复文件系统 |
  | 分区或盘符不见了 | 找回丢失的分区 → 按文件类型深度恢复 |
  | 磁盘有坏道 / 读写很慢或报错 | 坏道检测 → 制作磁盘镜像 → 在镜像上找回删除的文件或按文件类型深度恢复 |

- **全部功能**：七个功能平铺成两列卡片，能用的在前，给已经知道要用什么的用户直达。
- **关于**：程序版本、恢复引擎是否可用（每次打开现查 `engine.capabilities`）；引擎版本与支持的操作折叠在「技术细节」里。

功能卡片写明功能做什么、适合与不适合的情况。还没做的功能（找回丢失的分区、修复打不开的分区、检查并修复文件系统）卡片变淡、虚线边框，带「开发中」文字标签，不只靠颜色区分；仍然可以用 Tab 聚焦，标 `aria-disabled="true"`，读屏软件先读到原因，点击不进入。问题、功能与推荐顺序集中在 `navigation.ts`，文案在 `problems.*`、`features.*` 下（症状与注意事项是字符串数组，条数随语言可以不同）。

导航页与功能页在同一页面里用条件渲染切换，不用路由。焦点：在导航栏切换时留在导航项上；从首页点问题卡片时落在问题页标题；进入功能页时落在功能页标题；从功能页「返回」时回到进入前的导航页，落在刚才点的那张卡片上。进入功能页时导航栏收起：功能运行中不能离开（「返回」按钮此时不可用），导航栏留着会绕过这个限制。

每个向导的步骤是：选择磁盘或镜像 → 分析 → 确认结果 → 执行 → 报告。任何向导在读到介质错误时，都会建议先转去制作镜像，再在镜像上继续。

已接入的功能页是「找回删除的文件」「按文件类型深度恢复」「坏道检测」与「制作磁盘镜像」。它们共用来源选择（`SourcePicker`）和框架样式（`styles/wizard.css`），两个向导还共用预览展示（`FilePreviewView`）。

**坏道检测**（`BadSectorCheck`）是读取扫描（`disk.readScan`）的界面：把整块盘或镜像从头到尾顺序读一遍（每次 1 MiB，读不出就跳过、不重试），报告读取字节、读不出的区段数与字节数、用时；有读不出的区段时列出前 20 段的起始位置与长度，引擎最多记 1000 段，超出时说明总字节数仍包括全部。页面上先写明结果怎么看（没有读不出的区段、有读不出的区段、读速偏低、只读一次的局限），结果下方按有没有读不出的区段给出下一步：有坏道且数据重要时先做镜像，再在镜像上恢复。

深度恢复向导分四步：

1. **来源**：镜像文件（路径框，或系统的选择文件对话框）或物理磁盘（与坏道检测共用磁盘列表）。
2. **格式**：列表来自 `carve.listFileTypes`，默认勾选各格式的默认设置；格式名按扩展名取本地化文案。
3. **保存位置**：先选什么时候保存——「扫描时直接保存」（默认）或「先只扫描，扫完再挑选要保存的文件」。前者用系统的选择文件夹对话框，路径框也可以直接编辑，源为物理磁盘时提示输出必须在另一块盘上，开始时由引擎再核对一次（第 5.4 节）；后者这一步不用选目录。
4. **开始**：进度与读速、按格式统计的已找到数量和大小，可以取消；结束后显示报告和实际输出目录。运行中不能返回上一步或离开。找到的文件边扫边列在下方：
   - 左边是两级树，可以按格式或按磁盘位置分组。按位置分组时，每段的大小取 2 的幂，至少 1 MiB，段数不超过 32。单击分组展开或收起，单击文件在右边看详情与预览，双击文件用系统默认程序打开；键盘上下移动、左右收起展开、回车打开。行高固定，只渲染看得见的行，十万级文件也不卡；
   - 右边是详情（文件名、格式、大小，起始与结束位置：结束位置是最后一个字节，各给出字节偏移与扇区号）、预览（第 6.3 节），以及「用默认程序打开」「在文件夹中显示」；
   - 扫描中、完成后、取消后都能查看。选中文件 150 毫秒后才请引擎读取，方向键快速移动时不为途经的每个文件起一个引擎；晚到的旧答复丢弃。
   - 只扫描时：每行有勾选框（空格也能勾选，勾选分组即选中整组），预览直接从源上读；扫描结束（完成或取消）后，在下方选保存位置、点「保存选中的 N 个文件」，显示保存进度、没能保存的文件与原因、已保存数。双击还没保存的文件，先把它保存到保存位置再打开；没保存的文件不能「在文件夹中显示」。还有没保存的结果时，离开、返回或重新扫描前先确认。

找回删除的文件向导分三步：

1. **来源**：同深度恢复。点「下一步」时打开浏览会话、读出分区表，物理磁盘这时请求提权。
2. **分区**：表格列出编号、卷标、文件系统、用途、起始位置、大小，读分区表时的说明列在上方；不能浏览的分区置灰并写明原因（BitLocker 已加密、认不出、NTFS 的 `$MFT` 读不出等）。NTFS 分区点「下一步」先扫描 MFT：进度条与已读、总字节数，可以取消（留在这一步，下次重扫），失败时写明原因；扫过的分区再进入不重扫。回到来源这一步时关闭会话。
3. **浏览与复制**：
   - 左边是分区的目录树：单击文件夹展开或收起，第一次展开时才向引擎要内容，按页加载，「还有 N 项」的行滚进视野就加载下一页；行高固定、只渲染看得见的行。已删除的项名字划线、变淡，并带「已删除 · 可能完整 / 已被覆盖 / 无法判断」的文字标签，不只靠颜色区分；可以只看已删除的文件（目录都保留）。每行一个勾选框，空格勾选；上级目录已勾选的项不再单列；
   - 存放方式不支持的项（NTFS 压缩、加密、系统压缩、链接）另带「… · 暂不支持」的文字标签，详情里写明原因，不预览、不打开；「找不到原目录的文件」是斜体的虚拟目录；
   - NTFS 分区上方写明扫描结果（记录数、已删除数、找不到原目录的数、读不出的记录数），下方提示时间是 UTC；
   - 右边是详情（名字、短文件名、路径、状态说明、存放方式、大小、修改与创建时间，NTFS 标注 UTC、数据位置、MFT 记录号）与预览；
   - 双击文件或点「用默认程序打开」：先把它复制到保存位置（还没选时先弹出选择文件夹），复制好再交给系统打开；可执行与脚本类文件不打开，改为在文件夹中显示；
   - 下方是保存位置与「复制选中的 N 项」，进度（NTFS 先扫描 MFT 时显示扫描进度）、失败清单与内容全为 0 的文件清单（各最多列 20 个）、汇总与「在文件夹中显示」。复制进行中不能返回或离开。
   - 源是物理磁盘时提示：分区正在使用时读到的可能不是最新状态，找回删除的文件前先停止往这块盘写东西。

**制作磁盘镜像**（`DiskImage`）是 `image.create` / `image.resume` 的界面：页面上先写明怎么做的（三轮读取、坏区图、随时停止与续做、空间要求）。表单分两组，各有标题和一句说明：「① 要复制的盘（来源）」默认选物理磁盘（做镜像通常是为了出问题的盘），选镜像文件时说明这是把已有镜像再复制一份；「② 镜像保存到」的「镜像保存为」填新镜像文件的完整路径，说明会新建一个与来源一样大的文件、旁边另存同名加 `.map` 的坏区图。「选择文件夹…」选好文件夹后自动接上默认文件名（物理盘为 `disk<编号>.img`，镜像文件为 `<原文件名>-image.img`，同一个源每次给出同一个名字，续做时容易对上）；源为物理磁盘时提示镜像必须在另一块盘上。运行中显示当前轮次、已读出与总容量、读不出的字节数、还没读完的三类字节数、读速，复制这一轮另给出预计剩余时间；进度条按「已经有结论的字节数」（读出或确认读不出）走。「停止（之后可以继续）」存好坏区图后结束；停止后、源设备读不到之后都显示「继续制作」，按同一个源、同一路径续做。新建时这个位置已有镜像（`imageExists`）显示「继续上次的镜像」。完成后报告读出、读不出的区段数与字节数、本次用时、镜像与坏区图的路径，列出前 20 段读不出的位置，并提示在「找回删除的文件」或「按文件类型深度恢复」里选这个镜像文件；有读不出的位置时说明它们在镜像里是 0。

坏道检测（读取扫描）、深度恢复、浏览会话、复制、制作镜像共用同一套任务状态（`useJob`：启动、取消、进度、无响应与恢复、终结），各自只处理自己的结果。

**专家模式**展开全部参数和实时日志，保证所有能力都有入口。

### 6.2 可视化

- 分区布局条：按比例显示分区、空闲区和找到的候选分区。
- 扫描扇区图：已扫描、已恢复、坏区分色显示；制作镜像时显示坏区图中各区段的状态。
- 检查结果：问题清单按严重程度分组，每项可以展开看位置、影响和修法。
- 恢复统计：按文件类型统计数量和大小。
- 写入前对比：修改前和修改后的分区表、引导扇区差异。

### 6.3 预览安全

恢复出的文件**不交给 WebView 直接渲染**。图片由引擎解码后生成缩略图；文本转义后以纯文本显示；其他类型只显示元数据和十六进制视图。恢复出的 HTML、SVG 等文件在 WebView 中会执行脚本。

目前的实现（深度恢复的结果）：

- 宿主每次预览起一个一次性引擎调用 `preview.file`，与列盘、列格式一样，查完即退出；解码只在没有特权的引擎进程里进行。
- 内容是 JPEG 或 PNG（按文件头判断，不看扩展名）时解码，缩到最长边 512 像素（小图不放大），重新编码成 PNG，以 `data:` 地址交给界面显示（CSP 的 `img-src` 已允许 `data:`）。超过 64 MiB 的图片不解码；解码限制边长 16384、内存 256 MiB，残缺或伪造的图片只回「无法显示」和原因。
- 其他格式显示开头 4 KiB 的十六进制与 ASCII。现有格式都不是文本，纯文本预览等有文本格式时再加。
- 「找回删除的文件」里的文件同样由引擎读取、解码（`repair.previewFile`），内容直接从源盘读，规则与上面相同；文件本身不写到任何地方，也不交给 WebView。
- 预览、打开、在文件夹中显示都只接受任务 ID 加恢复时起的文件名（`f` 加十位数字、`.`、1 到 8 位小写字母或数字），宿主在该任务的输出目录里找，不接受其他路径。输出目录取自 `carve.start` 或 `carve.extract` 的答复，宿主记到退出为止，任务结束后仍可查看。
- 只扫描、还没保存的文件：界面只给扫描任务 ID 加 偏移、长度，宿主回到这个扫描任务的源上（同一个镜像，或请代理重新打开同一块磁盘），另起引擎调用 `preview.range`；读超出源末尾的部分截掉。
- 「用默认程序打开」交给系统，按文件类型由对应程序处理，不经过 WebView。

## 7. 宿主

- 管理引擎进程与代理进程的启动、心跳、退出。引擎程序与宿主程序放在同一目录；Windows 上以 `CREATE_NO_WINDOW` 启动，不弹出控制台窗口。
- 把引擎事件合并后转给界面，界面侧不直接面对高频事件。界面只收一个事件 `job-event`，载荷是 `{jobId, kind, data}`，`kind` 为 progress、found、copied、imaging、log、completed、failed、cancelled、unresponsive、responsive。
- 任务 ID 由界面生成（UUID），在调用启动命令之前就记下，避免事件先于命令返回到达时被丢掉；宿主只接受字母、数字和连字符。
- 返回给界面的错误是 `{code, detail}`：`code` 由界面翻译成当前语言，`detail` 是技术细节。引擎答复的错误码中，`SOURCE_UNAVAILABLE`、`OUTPUT_UNAVAILABLE`、`OUTPUT_ON_SOURCE` 分别转成 `sourceUnavailable`、`outputUnavailable`、`outputOnSource`，其余统一为 `engineRejected`。
- 磁盘代理在整个会话里只启动一次（第一次需要打开物理磁盘时），之后复用；宿主退出时代理随之退出。等待 UAC 期间，其他打开请求排队，不会同时弹出多个 UAC。代理程序同样放在宿主程序旁边，`tauri dev` / `tauri build` 会先编出引擎和代理。
- 本地保存任务记录，界面重启后可以看到历史任务并续传。
- Tauri 安全配置：严格 CSP；禁止加载远程内容；只开放白名单中的命令。系统文件对话框用官方的 dialog 插件，capability 只开放 `dialog:allow-open`（选择文件与文件夹）。
- 深度恢复只扫描时：`carve_preview_range`、`job_start_extract` 只接受扫描任务 ID，源取宿主记下的这个任务的源，界面不能借此读别的设备。保存任务的输出目录同样记下，保存好的文件按保存任务 ID 加文件名打开。
- 打开恢复出的文件、在文件夹中显示，用官方 opener 插件提供的 Rust 函数，由宿主自己的命令 `recovered_open`、`recovered_reveal` 调用。插件不注册、不开放给界面，界面无法让宿主打开任意路径。引擎答复的 `PREVIEW_UNAVAILABLE` 转成 `previewUnavailable`。
- 浏览分区：`browse_open` 起浏览任务（与扫描一样，物理盘先请代理复制只读句柄），`browse_list`、`browse_preview` 转给这个任务的引擎，等答复最多 120 秒（十万级目录、慢速 USB 盘）；`browse_scan` 等到扫完（有进度、可以用 `browse_cancel_scan` 停下，上限 24 小时）；关闭浏览用 `job_cancel`。复制用 `job_start_copy`。引擎的 `FS_UNAVAILABLE` 转成 `fsUnavailable`。
- 制作镜像用 `job_start_image`（源、镜像文件的完整路径、是否续做），分别转成 `image.create`、`image.resume`；物理盘与其他任务一样先请代理复制只读句柄。引擎的 `IMAGE_EXISTS`、`IMAGE_MISMATCH` 转成 `imageExists`、`imageMismatch`；`job.imaging` 转成 kind 为 imaging 的事件。
- 复制出的文件用 `copied_open`、`copied_reveal` 打开或在文件夹中显示：只接受任务 ID 加引擎报告的相对路径，路径只能由普通的路径分量组成，解析（含联接与符号链接）后必须仍在该任务的输出目录之内。找回的文件来路不明，`.exe`、`.bat`、`.cmd`、`.ps1`、`.vbs`、`.js`、`.hta`、`.msi`、`.lnk`、`.url`、`.reg`、`.scr` 等可执行、脚本或会改系统设置的类型不交给系统打开（`executableBlocked`），只能在文件夹中显示。

## 8. 质量目标的设计约束

| 目标 | 约束 |
|---|---|
| **高可用** | 进程隔离，引擎故障不影响界面；深度恢复和镜像都能断点续传；心跳与无响应处理；任务记录持久化；输出盘满自动暂停；连续读错误时暂停并提示检查连接 |
| **鲁棒** | 解析器对任意输入只返回结果或"不认识"，不 panic：禁用 `unwrap`/`expect`/直接下标，来自磁盘的数值一律用带检查的运算；panic 在任务边界捕获并转成任务失败；写入计划带前置哈希、备份、读回校验和回滚；磁盘报错时先镜像后修复，检查与修复分开 |
| **安全** | 解析代码不持有特权；引擎不具备写盘能力；默认只读，写盘必须进入修复模式；不监听端口；恢复文件不进 WebView；每个解析器都有 fuzz 目标；依赖经漏洞与合规检查；安装包签名 |
| **高性能** | 三段流水线；签名查找表；同盘顺序读、多盘并行；事件节流与批量合并；虚拟滚动；性能基准纳入持续集成 |
| **美观** | 统一的设计系统与主题；分区布局、扫描进度、恢复结果可视化 |
| **易用** | 按问题导航与场景向导；专家模式保留全部参数；写入前对比；双语；键盘可达；术语解释 |
